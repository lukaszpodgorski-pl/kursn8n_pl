Eksportujesz workflow ręcznie, klikając "Download" za każdym razem, gdy coś zmienisz - i czasem
zwyczajnie o tym zapominasz? Ten gotowiec robi to za Ciebie każdej nocy: pobiera wszystkie workflow
z Twojej instancji n8n przez jej własne API i zapisuje je jako pliki JSON w repozytorium GitHub.
Dostajesz to, czego zwykły plik na dysku nie daje - pełną historię zmian, commit po commicie.

To praktyczne domknięcie zasady backupu 3-2-1 z [Modułu 7: Produkcja](/modul-7-produkcja#backupy-3-2-1-i-testowane-odtwarzanie):
wersjonowanie definicji workflow w Git, dokładnie tak, jak opisuję w sekcji o backupach. Po drodze
ćwiczysz też coś, czego jeszcze nie robiłeś w kursie - wywołanie własnego API n8n z poziomu
workflow, node'em, który nazywa się po prostu **n8n**.

## Czego potrzebujesz

- **Moduł 7 ukończony** - a przynajmniej sekcję [Backupy 3-2-1 i testowane odtwarzanie](/modul-7-produkcja#backupy-3-2-1-i-testowane-odtwarzanie),

  API n8n bywa wyłączone administracyjnie na niektórych planach/wdrożeniach - jeśli Settings → n8n API
  nie istnieje w Twoim panelu, ten gotowiec nie zadziała bez zmiany konfiguracji.
- **Konto GitHub i puste repozytorium** przeznaczone na kopie workflow - może być prywatne.
- **Znajomość items i wyrażeń** z [Modułu 3: Praca z danymi](/modul-3-praca-z-danymi) oraz Code Node
  z [Modułu 5: Kod i sub-workflow](/modul-5-kod-sub-workflow) - w tym gotowcu Code Node robi realną robotę.

:::danger[Czego ten backup NIE robi]
API n8n, z którego korzysta ten workflow, eksportuje **definicje workflow** - node'y, połączenia,
parametry - ale **nie eksportuje credentials** w użytecznej, odtwarzalnej postaci ani zawartości
[Data Tables](/modul-2-interfejs-pierwszy-workflow#data-tables---wbudowane-tabele-danych) (workflow
zapisuje tylko odwołanie do tabeli, nie jej wiersze). Ten gotowiec to
wersjonowanie i możliwość odtworzenia logiki workflow, nie kompletny disaster recovery. Pełny backup,
który obejmuje też credentials, to kopia bazy danych plus bezpiecznie przechowany klucz
`N8N_ENCRYPTION_KEY` - dokładnie tak, jak opisuję w [Module 7 - sekcja o backupach](/modul-7-produkcja#backupy-3-2-1-i-testowane-odtwarzanie).
Traktuj te dwa mechanizmy jako uzupełniające się, nie zamienne.

## Budowa krok po kroku

### 1. Harmonogram - Schedule Trigger co noc o 3:00

Node **Schedule Trigger** ustawiony na interwał **Days** z wartością `1`, godziną `3` i minutą `0`
uruchamia workflow raz na dobę, w nocy - poza godzinami, gdy realnie edytujesz workflow na
produkcji. Szczegóły konfiguracji interwałów (w tym różnicę między Days, Hours i wyrażeniem cron)
znajdziesz w [dokumentacji Schedule Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.scheduletrigger/).
Jak w każdym gotowcu z triggerem czasowym - workflow musi być **opublikowany** (aktywny), żeby
Harmonogram w ogóle zadziałał.

Godzina `3:00` liczy się według strefy czasowej workflow. Plik JSON ma już zapisane
`Europe/Warsaw` w ustawieniach, ale po imporcie sprawdź to w **...** → **Settings** →
**Timezone** - bez strefy workflow n8n bierze strefę instancji, domyślnie nowojorską
([ustawienia workflow](https://docs.n8n.io/build/manage-workflows/configure-workflow-settings)).

### 2. Wygeneruj klucz n8n API i podłącz credentials

Zanim node n8n będzie mógł cokolwiek pobrać, potrzebujesz klucza do własnego API instancji:

<Steps>

1. W n8n przejdź do **Settings → n8n API**.
2. Wybierz **Create an API key**, nadaj etykietę (Label) i ustaw datę wygaśnięcia (Expiration).
3. Skopiuj wygenerowany klucz - zobaczysz go tylko raz.
4. W n8n utwórz nowe credentials typu **n8n API**: wklej klucz w pole **API Key**, a w polu
   **Base URL** wpisz adres API swojej instancji - dla self-hostingu w formacie
   `https://twoja-domena/api/v1`, dla n8n Cloud `https://twoja-instancja.app.n8n.cloud/api/v1`.
5. Podepnij te credentials pod node'em **Pobierz workflow z n8n**.

</Steps>

Pełny opis generowania i użycia klucza znajdziesz w
[dokumentacji autentykacji API n8n](https://docs.n8n.io/connect/n8n-api/authentication). Traktuj
ten klucz jak hasło do całej instancji - na kontach bez planu Enterprise ma pełny dostęp do
wszystkich zasobów, nie tylko do odczytu workflow.

### 3. Pobierz workflow z n8n - resource Workflow, operacja Get Many

Node **n8n** to osobna kategoria node'ów w n8n - taka, która woła **własne** API instancji, a nie
usługę zewnętrzną. W tym gotowcu resource to **Workflow**, operacja **Get Many**, z włączonym
**Return All**. Pełny opis dostępnych resource'ów (Workflow, Execution, Credential, Audit) i
operacji znajdziesz w [dokumentacji node'a n8n](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.n8n/).

Operacja Get Many zwraca **jeden item na każdy workflow** - dokładnie ten sam mechanizm co przy
zwykłej liście rekordów z [Modułu 3: Praca z danymi](/modul-3-praca-z-danymi). Dzięki temu w tym
gotowcu **nie ma osobnego node'a Loop** - Code i GitHub, które idą dalej w łańcuchu, same
przetworzą każdy workflow po kolei, bo n8n domyślnie iteruje po itemach bez dodatkowej pętli.

:::tip[Return All a paginacja API]
Sama REST API n8n zwraca wyniki stronami - domyślnie 100 workflow na stronę, maksymalnie 250
([dokumentacja paginacji API](https://docs.n8n.io/connect/n8n-api/pagination)). Dopóki w tym
node'cie **Return All** jest włączone (domyślna wartość), node sam przechodzi przez wszystkie
strony i dostajesz komplet workflow - to ważne przy większych instancjach, gdzie workflow jest
więcej niż 100.
:::

### 4. Przygotuj plik backupu - Code Node (Run Once for Each Item)

Node **Code** działa w trybie **Run Once for Each Item** - dokładnie tak, jak opisuję w
[Moduł 5: Kod i sub-workflow](/modul-5-kod-sub-workflow): `$json` to bieżący workflow, bez pętli.
Dla każdego workflow node buduje ścieżkę pliku ze slugu nazwy i ID, treść pliku jako sformatowany
JSON oraz treść commita:

```javascript
// $json to pojedynczy workflow - n8n przetwarza go osobno dla każdego itemu
// (patrz Moduł 3: Praca z danymi), bez potrzeby osobnej pętli.
const workflow = $json;

const folder = 'SCIEZKA_W_REPO';

const slug = workflow.name
  .toLowerCase()
  .replace(/ł/g, 'l')
  .normalize('NFD')
  .replace(/\p{Diacritic}/gu, '')
  .replace(/[^a-z0-9]+/g, '-')
  .replace(/^-+|-+$/g, '');

return {
  json: {
    sciezka: `${folder}/${slug}-${workflow.id}.json`,
    tresc: JSON.stringify(workflow, null, 2),
    wiadomoscCommit: `Backup workflow: ${workflow.name}`
  }
};
```

Czytając to krok po kroku:

- `.normalize('NFD').replace(/\p{Diacritic}/gu, '')` - rozdziela polskie znaki na literę i
  "ogonek" (znak diakrytyczny), a potem usuwa sam ogonek (`ą` → `a`, `ć` → `c`), żeby ścieżka
  pliku nie zawierała znaków, które bywają kłopotliwe w adresach URL i niektórych systemach plików.
- `.replace(/ł/g, 'l')` przed `normalize` - `ł` jest osobną literą, nie `l` z ogonkiem, więc NFD
  jej nie rozkłada. Bez tej linii "Złoty" daje slug `z-oty`.
- `.replace(/[^a-z0-9]+/g, '-')` - wszystko, co nie jest literą ani cyfrą (spacje, myślniki,
  znaki specjalne), zamienia na pojedynczy dywiz.
- `${workflow.id}` w nazwie pliku gwarantuje unikalność, nawet gdy dwa workflow nazywają się tak
  samo - sam slug nazwy do tego nie wystarczy.
- `JSON.stringify(workflow, null, 2)` formatuje JSON z wcięciami - czytelny w historii commitów
  GitHuba, nie jeden nieczytelny wiersz.

### 5. Zapisz w repozytorium GitHub - resource File, operacja Edit

Node **GitHub** w resource **File** ma pięć operacji: Create, Delete, Edit, Get i List
([dokumentacja node'a GitHub](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.github/)).
W tym gotowcu wybrana jest **Edit** - i to nieprzypadkowo. Operacja Edit sama pobiera aktualny SHA
pliku (skrót identyfikujący jego bieżącą wersję w Git) i dopiero z nim wysyła nadpisanie - to
mechanizm [Contents API GitHuba](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents),
który chroni przed przypadkowym nadpisaniem cudzej zmiany. Dzięki temu nie musisz sam zarządzać
SHA, jak przy gołym wywołaniu API. Operacja **Create** tego nie robi - nie sprawdza w ogóle, czy
plik już istnieje, więc użyta na ścieżce, pod którą coś już jest, po prostu zwróci błąd.

Pola `filePath`, `fileContent` i `commitMessage` wskazują wyrażeniami wprost na pola przygotowane
przez poprzedni node: `{{ $json.sciezka }}`, `{{ $json.tresc }}` i `{{ $json.wiadomoscCommit }}`.
Treść pliku możesz wpisać jako zwykły tekst - node sam zakoduje ją do Base64, którego wymaga API
GitHuba, nie musisz robić tego ręcznie.

:::caution[Nowy workflow, którego pliku jeszcze nie ma w repo]
Edit najpierw pobiera SHA istniejącego pliku, więc dla **świeżo dodanego** workflow (pliku jeszcze
nie ma w repo) kończy się błędem - nie ma czego pobrać
([`getFileSha` w kodzie node'a GitHub](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Github/Github.node.ts)).
Bez obsługi błędu to nie jest problem "jednego workflow": pierwszy brakujący plik przerywa cały
node, więc tej nocy nie zapisuje się już żaden kolejny workflow, a każdy nowy workflow psuje
backup aż do ręcznej interwencji.

Dlatego gotowiec ma to rozwiązane na stałe. W node'cie **Zapisz w repozytorium GitHub** otwórz
**Settings** i ustaw **On Error** na _Continue (using error output)_ - node dostaje drugie
wyjście, na które trafiają tylko itemy zakończone błędem. Do tego wyjścia podłącz drugi node
**GitHub** (w pliku: **Utwórz nowy plik w repozytorium**) z operacją **Create**. Item na wyjściu
błędu niesie już tylko komunikat błędu, więc pola bierzesz wprost z node'a Code:
`{{ $('Przygotuj plik backupu').item.json.sciezka }}`, analogicznie `tresc`
i `wiadomoscCommit`. Pozostałe workflow zapisują się normalnie przez Edit.
:::

### 6. Podłącz credentials GitHub - Personal Access Token

Node GitHub potrzebuje własnych credentials, osobnych od tych z kroku 2. n8n zaleca **Personal
Access Token (classic)** zamiast tokena fine-grained - ma mniej ograniczeń
([dokumentacja credentials GitHub](https://docs.n8n.io/integrations/builtin/credentials/github/)).

<Steps>

1. Na GitHubie przejdź do **Settings → Developer settings → Personal access tokens → Tokens
   (classic)**.
2. Wybierz **Generate new token (classic)**, nadaj opisową nazwę (np. "n8n - backup workflow") i
   ustaw datę wygaśnięcia.
3. Zaznacz **wyłącznie** scope **repo** - to minimalny zakres, który pozwala node'owi GitHub
   czytać i zapisywać pliki w repozytorium. Nie zaznaczaj nic więcej.
4. Skopiuj token i wklej go w nowe credentials typu **GitHub API** w n8n, razem ze swoją nazwą
   użytkownika GitHub.
5. Podepnij te credentials pod node'em **Zapisz w repozytorium GitHub**.

</Steps>

## Co może pójść nie tak

### 401 z API n8n - zły albo wygasły klucz

- **Objaw:** node "Pobierz workflow z n8n" kończy się błędem `401 Unauthorized`.
- **Przyczyna:** klucz API wygasł (miał ustawioną datę wygaśnięcia) albo został usunięty w
  **Settings → n8n API**, albo w credentials wpisana jest zła **Base URL** - przy self-hostingu to
  częsty błąd: brak `/api/v1` na końcu adresu, `http` zamiast `https`, albo adres, pod którym ten
  proces n8n faktycznie nie odpowiada.
- **Naprawa:** sprawdź w **Settings → n8n API**, czy klucz nadal istnieje i ma ważną datę wygaśnięcia.
  Przy self-hostingu upewnij się, że Base URL kończy się dokładnie na `/api/v1` i wskazuje ten sam
  adres, pod którym normalnie otwierasz panel n8n.

### GitHub zwraca błąd przy zapisie pliku (SHA / konflikt)

- **Objaw:** node "Zapisz w repozytorium GitHub" (operacja Edit) kończy się błędem podczas próby
  nadpisania pliku - najczęściej informacją o brakującym albo nieprawidłowym SHA, rzadziej wprost
  kodem `409 Conflict` z API GitHuba.
- **Przyczyna:** Edit najpierw pobiera aktualny SHA pliku i dopiero z nim wysyła nadpisanie (patrz
  krok 5). Błąd pojawia się, gdy plik o tej ścieżce jeszcze nie istnieje - najczęstszy przypadek to
  świeżo dodany workflow - albo gdy SHA zdążył się zmienić między odczytem a zapisem, bo dwa
  uruchomienia próbowały nadpisać ten sam plik niemal równocześnie (np. nakładający się ręczny test
  i harmonogram, albo wciąż trwające poprzednie wykonanie).
- **Naprawa:** sprawdź, czy node **Zapisz w repozytorium GitHub** ma w **Settings** ustawione
  **On Error** na _Continue (using error output)_ i czy do jego wyjścia błędu jest podłączony node
  **Utwórz nowy plik w repozytorium** (patrz krok 5) - bez tego pierwszy nowy workflow zatrzymuje
  backup całej nocy. Jeśli błąd pojawia się w node'cie Create, plik pod tą ścieżką już istnieje,
  a Edit zawiódł z innego powodu - jego komunikat zobaczysz w danych wykonania. Jeśli podejrzewasz nakładające się uruchomienia,
  sprawdź w zakładce **Executions**, czy poprzednia noc na pewno się zakończyła, zanim wystartowała
  kolejna.

### Duża instancja - w repo brakuje części workflow

- **Objaw:** w repozytorium brakuje plików dla części workflow, mimo że w n8n istnieją.
- **Przyczyna:** REST API n8n paginuje wyniki - domyślnie 100 workflow na stronę, maksymalnie 250
  ([dokumentacja paginacji](https://docs.n8n.io/connect/n8n-api/pagination)). Node z wyłączonym
  **Return All** (albo ręcznie ustawionym, niskim **Limit**) pobierze tylko pierwszą stronę wyników.
- **Naprawa:** upewnij się, że w node'cie "Pobierz workflow z n8n" pole **Return All** jest włączone
  (domyślna wartość) - wtedy node sam przechodzi przez wszystkie strony za Ciebie.

### Token GitHub ma zbyt szeroki zakres uprawnień

- **Objaw:** to nie awaria workflow, tylko ryzyko bezpieczeństwa - token użyty w credentials może
  zrobić w Twoich repozytoriach więcej, niż ten workflow faktycznie potrzebuje.
- **Przyczyna:** przy generowaniu tokena classic łatwo zaznaczyć więcej scope'ów "na wszelki
  wypadek" albo zostawić dostęp do wszystkich repozytoriów zamiast jednego, dedykowanego.
- **Naprawa:** ogranicz token do scope **repo** (patrz krok 6) i, jeśli to możliwe, do jednego
  repozytorium przeznaczonego wyłącznie na te kopie. Token używany tylko przez ten workflow nie
  powinien mieć dostępu do niczego więcej.

## A jeśli nie GitHub?

GitHub to tylko jedno z miejsc, do których możesz odkładać kopie. Jeśli Twoja firma siedzi na
GitLabie, trzymasz kod na własnym Gitea, a może w ogóle nie chcesz Gita i wolisz zwykły katalog
w chmurze - pierwsze trzy node'y gotowca zostają **bez zmian**. Harmonogram, node n8n i Code
przygotowują dokładnie to samo: ścieżkę pliku (`sciezka`), treść JSON (`tresc`) i opis
(`wiadomoscCommit`). Wymieniasz tylko ostatni node - ten, który zapisuje.

Różnią się trzy rzeczy: czy n8n ma do danej usługi **wbudowany node** (gotowy klocek z formularzem)
czy musisz wołać API przez **HTTP Request**, jak usługa radzi sobie z plikiem, który już istnieje,
i skąd bierzesz **historię zmian**. Wszystko poniżej sprawdziłem w dokumentacji n8n i dostawców
w listopadzie 2026.

### GitLab - wbudowany node, najmniej zmian

n8n ma wbudowany [node GitLab](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.gitlab/)
z resource **File** i tymi samymi operacjami co GitHub: Create, Delete, Edit, Get i List. Podmieniasz
node GitHub na GitLab, wybierasz **File → Edit** i podpinasz te same wyrażenia: `{{ $json.sciezka }}`
w ścieżce pliku, `{{ $json.tresc }}` w treści, `{{ $json.wiadomoscCommit }}` w opisie commita,
plus nazwę gałęzi.

Co jest inaczej niż w GitHubie:

- **Właściciel projektu** w polu Project Owner. Jeśli repozytorium leży w podgrupie, wpisujesz
  całą ścieżkę grup z ukośnikami zamienionymi na `%2F`, np. `firma%2Fdevops%2Fbackupy` - tak każe
  dokumentacja node'a.
- **Własny GitLab (self-managed)** - w credentials typu
  [GitLab API](https://docs.n8n.io/integrations/builtin/credentials/gitlab/) wpisujesz adres swojego
  serwera w polu GitLab Server. n8n zaleca token z zakresem `api`.
- **Bez SHA.** API GitLaba nie wymaga, żebyś przy aktualizacji podawał skrót bieżącej wersji pliku
  ([dokumentacja Repository Files API](https://docs.gitlab.com/api/repository_files/)). Logika
  pierwszego uruchomienia zostaje jednak ta sama co w kroku 5: Create zakłada nowy plik, Edit
  aktualizuje istniejący.

### Gitea i Forgejo - HTTP Request, za to jeden commit na całą noc

Do Gitea i Forgejo (oraz Codeberga, który stoi na Forgejo) n8n **nie ma wbudowanego node'a** -
strona integracji [n8n i Gitea](https://n8n.io/integrations/gitea) odsyła do node'a **HTTP Request**.
Istnieją community nodes (paczki od społeczności, instalowane osobno), ale to nieoficjalny kod
i przed instalacją na produkcji warto sprawdzić, kto go utrzymuje.

Dobra wiadomość: API Gitea pozwala zapisać **wszystkie pliki w jednym commicie**. Endpoint
`POST /api/v1/repos/{właściciel}/{repo}/contents` przyjmuje tablicę `files`, a od Gitea 1.25
każda pozycja może mieć operację `upload` - "utwórz albo zaktualizuj", bez sprawdzania, czy plik
już istnieje ([specyfikacja API Gitea](https://gitea.com/api/swagger)). Znika cały problem
z pierwszym uruchomieniem. Code przełączasz wtedy w tryb **Run Once for All Items** i budujesz
jedno zapytanie zamiast wielu:

```javascript
// Run Once for All Items - wszystkie workflow w jednym commicie
const folder = 'SCIEZKA_W_REPO';

const files = $input.all().map(({ json: workflow }) => {
  const slug = workflow.name
    .toLowerCase()
    .replace(/ł/g, 'l')
    .normalize('NFD')
    .replace(/\p{Diacritic}/gu, '')
    .replace(/[^a-z0-9]+/g, '-')
    .replace(/^-+|-+$/g, '');

  return {
    operation: 'upload',
    path: `${folder}/${slug}-${workflow.id}.json`,
    // API Gitea wymaga treści zakodowanej w Base64
    content: Buffer.from(JSON.stringify(workflow, null, 2)).toString('base64')
  };
});

return [{ json: { branch: 'main', message: `Backup ${files.length} workflow`, files } }];
```

Node HTTP Request ustawiasz tak:

- **Method** `POST`, **URL** `https://twoj-gitea/api/v1/repos/WLASCICIEL/REPO/contents`.
- **Authentication** - Generic Credential Type → **Header Auth**: nazwa nagłówka `Authorization`,
  wartość `token TWOJ_TOKEN` (słowo `token`, spacja, token wygenerowany w ustawieniach konta Gitea).
- **Body** - JSON, wartość `{{ JSON.stringify($json) }}`.

:::caution[Forgejo i starsze Gitea]
Operacja `upload` doszła w Gitea 1.25. Forgejo (w tym Codeberg) i Gitea 1.24 znają tylko
`create`, `update` i `delete`, a `update` wymaga SHA bieżącej wersji pliku - tak jak GitHub
pod spodem. Wtedy zostajesz przy wariancie "item po itemie": HTTP Request z `GET` na
`/contents/{ścieżka}` pobiera SHA, przy błędzie 404 kierujesz item do `POST` (utworzenie pliku),
a przy sukcesie do `PUT` z polem `sha`. Do rozgałęzienia wystarczy ustawienie node'a
**On Error → Continue (using error output)**. Sprawdź wersję swojej instancji w stopce panelu,
zanim wybierzesz wariant.
:::

Gdzie trzymać takie repozytorium? Najprościej na własnym serwerze - Gitea i Forgejo to lekkie
aplikacje, które postawisz obok n8n tym samym Docker Compose. Codeberg pozwala na prywatne treści
tylko w małej skali (do 100 MB) i tylko osobom, które realnie rozwijają wolne oprogramowanie -
nie jest to hosting prywatnych kopii ([FAQ Codeberga](https://docs.codeberg.org/getting-started/faq/)).

### Bitbucket - HTTP Request, zapis bez SHA

W n8n istnieje tylko [Bitbucket Trigger](https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.bitbuckettrigger/) -
node, który _reaguje_ na zdarzenia w repozytorium, ale niczego do niego nie zapisuje. Zapis robisz
więc przez **HTTP Request** do endpointu `POST https://api.bitbucket.org/2.0/repositories/{workspace}/{repo}/src`
([dokumentacja Bitbucket Cloud REST API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-source/)).

Ten endpoint jest wygodniejszy niż GitHub: tworzy commit, który **dodaje albo nadpisuje** plik,
więc nie ma SHA i nie ma problemu pierwszego uruchomienia. Format jest za to nietypowy - nazwa pola
formularza to ścieżka pliku w repo, a wartość to jego treść:

- **Method** `POST`, **Body Content Type** `Form Urlencoded`.
- Pole o nazwie `/{{ $json.sciezka }}` i wartości `{{ $json.tresc }}`. Ukośnik na początku jest
  ważny: bez niego plik nazwany np. `message` zostałby wzięty za opis commita, nie za plik.
- Pole `message` z wartością `{{ $json.wiadomoscCommit }}` i opcjonalnie `branch`.
- **Authentication** - Basic Auth: login to adres e-mail konta Atlassian, hasło to
  [API token](https://support.atlassian.com/bitbucket-cloud/docs/using-api-tokens/) z uprawnieniami
  `read:repository:bitbucket` i `write:repository:bitbucket`.

### Nextcloud - wbudowany node, katalog zamiast Gita

Jeśli nie potrzebujesz Gita, a masz własną chmurę plików, [node Nextcloud](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.nextcloud/)
ma resource **File** z operacją **Upload**. Wyłączasz w nim Binary File, w File Path wpisujesz
pełną ścieżkę, np. `/Backup/n8n/{{ $json.sciezka }}`, a w File Content `{{ $json.tresc }}`.
Node wysyła plik przez WebDAV metodą `PUT`, która po prostu **nadpisuje** istniejący plik - nie ma
tu rozróżnienia Create/Edit. Katalog docelowy załóż raz ręcznie (albo operacją Folder → Create),
bo upload do nieistniejącego folderu się nie powiedzie.

W [credentials Nextcloud](https://docs.n8n.io/integrations/builtin/credentials/nextcloud/) podajesz
adres WebDAV: adres Twojej chmury z dopisanym `/remote.php/webdav`. Załóż do tego osobne hasło
aplikacji w ustawieniach bezpieczeństwa Nextclouda, nie używaj głównego hasła konta.

Historii commitów tu nie ma. Jest za to aplikacja Versions: Nextcloud zachowuje poprzednie wersje
nadpisanego pliku, ale je przerzedza (po 30 dniach zostaje jedna wersja na tydzień) i nie zajmuje
na nie więcej niż połowę wolnego miejsca użytkownika ([podręcznik Nextcloud - wersje plików](https://docs.nextcloud.com/server/latest/user_manual/en/files/version_control.html)).
Na kopie zapasowe to wystarcza, na przeglądanie, co dokładnie zmieniło się we wtorek, już nie.

### S3 i Backblaze B2 - wbudowany node, kopia poza Twoim serwerem

Magazyny obiektowe zgodne z S3 obsługujesz dwoma wbudowanymi node'ami:
[AWS S3](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.awss3/) dla Amazona
i [S3](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.s3/) dla pozostałych
dostawców zgodnych z S3 (dokumentacja wymienia m.in. MinIO, Wasabi i DigitalOcean Spaces; tak samo
podłączysz Backblaze B2). W obu wybierasz **File → Upload**, nazwę bucketu, w File Name nazwę pliku,
a w Parent Folder Key folder.

Różnice względem GitHuba:

- **Credentials** typu [S3](https://docs.n8n.io/integrations/builtin/credentials/s3/) mają pola
  S3 Endpoint, Region, Access Key ID i Secret Access Key - endpoint i klucze znajdziesz w panelu
  dostawcy przy buckecie.
- **Upload nadpisuje** obiekt o tej samej nazwie, więc znowu nie ma problemu pierwszego uruchomienia.
- **Treść jako tekst** - przy wyłączonym Binary Data node przyjmie `{{ $json.tresc }}` wprost
  w polu File Content. Plik dostaje wtedy typ `text/html` zamiast `application/json`; dla kopii to
  bez znaczenia, a jeśli Ci przeszkadza, zamień treść na plik node'em
  [Convert to File](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.converttofile/)
  i wyślij ją jako binarną.
- **Historia** - albo włączasz wersjonowanie obiektów w ustawieniach bucketu, albo dopisujesz datę
  do ścieżki (np. `backup/2026-11-09/...`) i każdej nocy powstaje nowy komplet. Przy drugim wariancie
  ustaw regułę cyklu życia (lifecycle), która po kilkudziesięciu dniach usuwa stare foldery.

To jedyny wariant, który z definicji ląduje **poza Twoim serwerem i poza Gitem** - dobra "kopia
poza siedzibą" z zasady 3-2-1. Backblaze B2 daje 10 GB za darmo, a potem kosztuje od 6,95 USD
za TB miesięcznie ([cennik Backblaze B2](https://www.backblaze.com/cloud-storage/pricing), stan na
listopad 2026) - kopie workflow zajmują zwykle pojedyncze megabajty.

na końcu workflow postawić dwa node'y zapisu obok siebie i mieć jedno i drugie.

## Jak to rozbudować

- **Commit message z datą** - dopisz do `wiadomoscCommit` w Code Node aktualną datę (np. przez
  `$now` z [Modułu 5: Kod i sub-workflow](/modul-5-kod-sub-workflow)), żeby historia commitów była
  czytelna na pierwszy rzut oka, bez rozwijania szczegółów.
- **Osobny branch na backupy** - zamiast pisać wprost do `main`, ustaw w polu Branch (Additional
  Parameters node'a GitHub) dedykowaną gałąź na kopie, np. `backups` - trzymasz historię backupów
  osobno od głównej linii repozytorium.
- **Powiadomienie o niepowodzeniu** - podepnij Error Trigger (patrz [Moduł 5: Kod i sub-workflow](/modul-5-kod-sub-workflow),
  sekcja o obsłudze błędów), żeby dostać alert, gdy nocny backup się nie powiedzie - inaczej cicha
  awaria potrafi trwać tygodniami, zanim ją zauważysz.
- **Rozróżnienie Create/Edit przez Get i IF** - zamiast wyjścia błędu z kroku 5 możesz dodać
  przed node'em GitHub operację **Get** z ustawieniem **On Error** → _Continue_ (dawniej
  **Continue On Fail**, patrz [Moduł 5](/modul-5-kod-sub-workflow)) i node IF sprawdzający, czy
  plik już istnieje - w zależności od wyniku kieruj do Create albo Edit. To o jedno zapytanie do
  GitHuba więcej na każdy workflow, za to błąd Edit z innego powodu nie wpada w gałąź Create.
- **Backup tylko zmienionych workflow** - zamiast zapisywać wszystko co noc, porównaj pole
  `updatedAt` z poprzednim zapisanym stanem (np. w osobnym pliku albo arkuszu) i pomiń workflow,
  które się nie zmieniły - mniej commitów, ta sama kompletność.

<Takeaways title="Co warto zapamiętać">
  - Node n8n woła własne API instancji - resource Workflow, operacja Get Many zwraca jeden item na
    każdy workflow, więc dalsze node'y iterują bez osobnej pętli.
  - Klucz n8n API generujesz w Settings → n8n API; credentials do niego mają dwa pola - API Key i
    Base URL (self-hosted kończy się na `/api/v1`).
  - W node'cie GitHub Edit sam pobiera SHA pliku przed nadpisaniem - Create tego nie robi i zawiedzie
    na istniejącym pliku; dla nowego pliku potrzebujesz Create, dla aktualizacji Edit.
  - Return All w node'cie n8n ma znaczenie realnie tylko przy dużych instancjach - REST API paginuje
    wyniki domyślnie po 100, maksymalnie 250.
  - Ten backup to wersjonowanie definicji workflow w Git, nie pełny disaster recovery - credentials i
    `N8N_ENCRYPTION_KEY` backupujesz osobno, jak w Module 7.
  - Poza GitHubem wymieniasz tylko ostatni node: GitLab, Nextcloud i S3 mają wbudowane node'y, Gitea,
    Forgejo i Bitbucket obsługujesz przez HTTP Request - a Bitbucket, Nextcloud, S3 i Gitea 1.25+
    nadpisują plik bez problemu pierwszego uruchomienia.
</Takeaways>
