## Przegląd interfejsu edytora

Edytor n8n (Editor UI) to miejsce, w którym powstają wszystkie automatyzacje. Zanim
zaczniesz klikać, warto wiedzieć, jak nazywają się jego elementy - będziemy się do nich
odwoływać przez cały kurs, a oficjalna dokumentacja używa tych samych nazw.

### Toolbar nad kanwą

U góry edytora znajdziesz nazwę workflow (kliknij, by ją zmienić), dostęp do tagów oraz
przycisk **Publish** w prawym górnym rogu (skrót `Shift + P`). Przycisku zapisu nie ma:
n8n zapisuje każdą zmianę automatycznie w ciągu kilku sekund, ale wszystkie edycje są
**szkicem**, dopóki nie opublikujesz workflow. Kliknięcie **Publish** otwiera okno, w którym
możesz nazwać wersję i dodać opis. Dopiero opublikowany workflow działa sam: Schedule
Trigger odpala się o swojej porze, a webhooki i formularze odpowiadają pod Production URL.
Niepublikowany workflow uruchomisz tylko ręcznie, w testach z edytora. W n8n 1.x tę samą
rolę pełnił przełącznik **Active / Inactive** - jeśli trafisz na starszy tutorial,
"aktywuj workflow" czytaj jako "opublikuj workflow".

:::caution[Edycje po publikacji nie trafiają na produkcję same]
Produkcja zawsze używa **opublikowanej wersji**, nie Twoich ostatnich edycji. Jeśli
poprawisz opublikowany workflow, zmiany zapiszą się jako szkic, a przycisk pokaże stan
"Published, has changes" - opublikowany, ale z nieopublikowanymi zmianami. Żeby poprawka
zaczęła działać, kliknij **Publish** jeszcze raz. Opublikowany workflow rozpoznasz też na
liście Workflows po znaczniku na jego karcie, a wycofasz go opcją **Unpublish** z menu
obok przycisku **Publish**. Źródło:
[Save and publish workflows (docs.n8n.io)](https://docs.n8n.io/build/understand-workflows/save-and-publish-workflows/),
stan na listopad 2026.
:::

### Skróty klawiszowe

Myszką zrobisz w edytorze wszystko, ale kilkanaście skrótów skraca budowanie workflow
o połowę klikania. Poniżej te, których używam najczęściej. Na macOS `Ctrl` zamieniasz na
`Cmd`, a `Alt` na `Option`; skróty jednoklawiszowe (`N`, `P`, `D`, `1`) działają tak samo
na obu systemach, o ile kursor nie stoi w polu tekstowym.

| Windows / Linux | macOS | Co robi |
| --- | --- | --- |
| `N` | `N` | Otwiera panel node'ów - szukasz node'a po nazwie i wstawiasz go `Enter` |
| `Ctrl + K` | `Cmd + K` | Otwiera Command Bar (paletę poleceń) - akcje edytora wpisywane z klawiatury |
| `Shift + P` | `Shift + P` | Otwiera okno publikacji workflow (to samo co przycisk **Publish**) |
| `Ctrl + S` | `Cmd + S` | Otwiera menu obok **Publish** z opcją _Name version_ (nazwane wersje: Cloud Pro i Enterprise, self-hosted Business i Enterprise). Zapisywania nie ma, jest automatyczne |
| `Ctrl + Enter` | `Cmd + Enter` | Uruchamia cały workflow (to samo co **Execute workflow**) |
| `Ctrl + Z` / `Ctrl + Shift + Z` | `Cmd + Z` / `Cmd + Shift + Z` | Cofa / ponawia ostatnią zmianę |
| `Ctrl + Alt + N` | `Cmd + Option + N` | Tworzy nowy workflow |
| `Ctrl + C` / `Ctrl + V` | `Cmd + C` / `Cmd + V` | Kopiuje / wkleja zaznaczone node'y |
| `Ctrl + A` | `Cmd + A` | Zaznacza wszystkie node'y na kanwie |
| `Spacja` + przeciągnij | `Spacja` + przeciągnij | Przesuwa kanwę |
| `1` / `0` | `1` / `0` | Dopasowuje widok do całego workflow / resetuje powiększenie |
| `F2` | `F2` | Zmienia nazwę zaznaczonego node'a |
| `P` | `P` | Przypina dane zaznaczonego node'a (pinning, o nim niżej) |
| `D` | `D` | Dezaktywuje zaznaczony node - zostaje na kanwie, ale nie wykonuje swojej pracy |
| `Shift + S` | `Shift + S` | Dodaje sticky note (notatkę na kanwie) |
| `Ctrl + G` | `Cmd + G` | Grupuje zaznaczone node'y (szczegóły w sekcji o organizacji pracy) |

Do tego jeden skrót wewnątrz node'a: wpisanie `=` w pustym polu parametru przełącza je
w tryb wyrażeń (expressions), czyli w pole, w którym odwołujesz się do danych z wcześniejszych
kroków.

:::note[Źródło i aktualność]
Skróty zweryfikowałem w oficjalnej dokumentacji -
[Keyboard shortcuts (docs.n8n.io)](https://docs.n8n.io/build/keyboard-shortcuts/) - stan na
listopad 2026. Tam znajdziesz też pełną listę, łącznie z nawigacją strzałkami między node'ami.
Skróty publikacji (`Shift + P`, `Ctrl/Cmd + S` jako menu obok **Publish**) pochodzą ze strony
[Save and publish workflows](https://docs.n8n.io/build/understand-workflows/save-and-publish-workflows/).
n8n rozwija edytor szybko, więc jeśli w Twojej wersji któryś skrót nie reaguje, zajrzyj
najpierw do dokumentacji dla swojej wersji.
:::

## Twój pierwszy workflow - krok po kroku

Zbudujesz prosty, ale realny przepływ: **Schedule Trigger → HTTP Request → Set (Edit
Fields)**. Codziennie pobierze on dane z publicznego API i wyciągnie z odpowiedzi tylko to,
co potrzebne. Każdy workflow zaczyna się od triggera - bez niego n8n nie wie, kiedy ruszyć.

<Flow
  title="moj-pierwszy-workflow"
  alt="Schemat przepływu: Schedule Trigger, następnie HTTP Request, następnie Edit Fields"
  caption="Przepływ, który zbudujesz w tej sekcji: trigger czasowy, pobranie danych z API i wyciągnięcie potrzebnych pól."
  spec={`
    Schedule Trigger (codziennie 7:00):clock @green -> HTTP Request (GET z API):globe @blue
    HTTP Request -> Edit Fields (wybierz pola):pen-to-square @amber
  `}
/>

1. **Utwórz nowy workflow.** Na liście workflow (Overview) kliknij **Create Workflow**.
   Otworzy się pusta kanwa z polem _Add first step…_.
2. **Dodaj trigger (Schedule Trigger).** Kliknij **Add first step** → wybierz _On a
   schedule_. n8n doda node **Schedule Trigger**. W jego parametrach ustaw `Trigger Interval`
   na _Days_ i godzinę, np. 7:00. To on będzie codziennie startował przepływ.
3. **Dodaj node akcji (HTTP Request).** Najedź na trigger, kliknij **+** przy jego wyjściu i
   wyszukaj **HTTP Request**. W polu `URL` wpisz adres przykładowego API, np.
   `https://api.github.com/repos/n8n-io/n8n`, metoda `GET`.
4. **Ustaw pola w node Set (Edit Fields).** Dodaj kolejny node **Edit Fields (Set)**. Włącz
   tryb _Manual Mapping_ i utwórz pole `nazwa` z wartością z poprzedniego kroku, np.
   wyrażenie `{{ $json.full_name }}`, oraz `gwiazdki` = `{{ $json.stargazers_count }}`.
5. **Uruchom workflow.** Kliknij **Execute workflow** (przycisk u dołu kanwy). n8n wykona
   przepływ od triggera w trybie testowym i pokoloruje node'y, które zakończyły się
   sukcesem.
6. **Sprawdź wynik i nazwij workflow.** Otwórz node **Edit Fields** i spójrz na panel
   **Output** po prawej - zobaczysz przygotowane pola `nazwa` i `gwiazdki`. Zapisywać nie
   musisz, n8n robi to automatycznie. Nadaj workflow czytelną nazwę (kliknij nazwę u góry
   edytora).
7. **Opublikuj workflow.** Kliknij **Publish** w prawym górnym rogu edytora i potwierdź w
   oknie publikacji. Od tej chwili Schedule Trigger będzie startował przepływ codziennie
   o 7:00 bez Twojego udziału.

:::tip[Dlaczego akurat ta trójka]
To minimalny, ale kompletny wzorzec niemal każdej automatyzacji: **kiedy** (trigger) →
**skąd** (pobranie danych) → **co z tym zrobić** (transformacja). Gdy go zrozumiesz,
podmienisz tylko klocki - np. HTTP Request na Gmail, a Set na zapis do bazy - i schemat
zostanie ten sam.
:::

## Triggery: Manual, Schedule i Webhook

Trigger to node, który _rozpoczyna_ workflow. Od jego wyboru zależy, kiedy i jak Twoja
automatyzacja w ogóle ruszy. Na start wystarczy poznać trzy najczęstsze - różnią się tym,
**co** wyzwala wykonanie.

<CardGrid>
  <ConceptCard icon="fa-hand-pointer" title="Manual Trigger">
    **Ty** uruchamiasz przepływ klikając "Execute workflow". Idealny do nauki i testów - nie
    reaguje na nic z zewnątrz i nie działa po publikacji.
  </ConceptCard>
  <ConceptCard icon="fa-calendar-days" title="Schedule Trigger">
    **Czas** uruchamia przepływ - co kilka sekund, minut, godzin, dni, tygodni, miesięcy lub
    wg własnego wyrażenia cron. Do zadań cyklicznych: raporty, synchronizacje.
  </ConceptCard>
  <ConceptCard icon="fa-bolt" title="Webhook">
    **Zdarzenie z zewnątrz** uruchamia przepływ - inny system wysyła żądanie HTTP na unikalny
    URL. Do reakcji w czasie rzeczywistym (formularz, płatność, zdarzenie z innej aplikacji).
  </ConceptCard>
</CardGrid>

### Kiedy którego użyć

| Trigger | Co go wyzwala | Wymaga publikacji workflow? | Typowe zastosowanie |
| --- | --- | --- | --- |
| **Manual Trigger** | Kliknięcie "Execute workflow" w edytorze | Nie - działa tylko w teście | Nauka, testy, jednorazowe uruchomienia |
| **Schedule Trigger** | Harmonogram (interwał lub cron) | Tak - by uruchamiał się sam | Raporty cykliczne, synchronizacje, sprzątanie danych |
| **Webhook** | Przychodzące żądanie HTTP na URL | Tak - produkcyjny URL działa po publikacji | Formularze, płatności, integracje real-time, callbacki z API |

:::note[Schedule Trigger - interwały]
W parametrze `Trigger Interval` wybierasz jednostkę: _Seconds, Minutes, Hours, Days, Weeks,
Months_ albo _Custom (Cron)_ dla pełnej kontroli (np. `0 7 * * 1-5` = o 7:00 w dni robocze).
_Cron_ to standardowy, zwięzły zapis harmonogramu w formacie `minuta godzina dzień miesiąc dzień-tygodnia` -
gwiazdka oznacza "każdy". To następca dawnego node'a "Cron".
:::

:::caution[Jeden trigger startowy na workflow]
Workflow można mieć więcej niż jeden trigger, ale dane uruchomienie startuje od **jednego**
z nich. Nie mieszaj bez potrzeby - najczytelniej jest, gdy przepływ ma jeden, świadomie
wybrany punkt startu.
:::

## Uruchamianie i debugowanie

Budowanie workflow to pętla: uruchom → zobacz dane → popraw. n8n daje do tego komplet
narzędzi: pełne i częściowe wykonania, podgląd danych między node'ami, przypinanie danych
oraz pełną historię executions.

### Execute workflow vs Execute step

- **Execute workflow** - uruchamia cały przepływ od triggera. Używasz, gdy chcesz sprawdzić
  wszystko od początku do końca.
- **Execute step** (częściowe wykonanie) - uruchamia tylko zaznaczony node, korzystając z
  danych z poprzednich kroków. Bezcenne, gdy poprawiasz jeden node i nie chcesz znów
  przepuszczać całego przepływu.

### Podgląd danych między node'ami

Po każdym uruchomieniu połączenia na kanwie pokazują liczbę przepuszczonych itemów, a w
panelu node'a widzisz dane wejściowe (**Input**) i wynik (**Output**) w trzech widokach:
_Table_, _JSON_ i _Schema_. To tutaj sprawdzasz, czy dane mają taki kształt, jakiego
oczekujesz - większość błędów to po prostu inna nazwa pola niż się spodziewałeś.

:::tip[Pinning danych - oszczędzaj czas i limity API]
Opcją **Pin data** "zamrażasz" wynik node'a. Przy kolejnych testowych uruchomieniach n8n
użyje przypiętych danych zamiast ponownie wołać API - szybciej, taniej i zawsze na tym samym
zestawie danych (łatwiej porównywać efekty zmian). Przypięcie zdejmiesz przez **Unpin
data**.

**Ważne:** pinning działa tylko w edytorze, przy wykonaniach ręcznych i częściowych. W
opublikowanym workflow przypięte dane są ignorowane - produkcja zawsze pobiera dane "na żywo".
:::

### Lista i szczegóły executions

Zakładka **Executions** w workflow (i globalne "All executions") to dziennik uruchomień.
Każde ma status - **Success**, **Error** lub **Running** - oraz tryb: _manual_, _trigger_
(produkcyjne) albo częściowe. Klikając wykonanie, otwierasz jego kopię na kanwie z
dokładnymi danymi z tamtego momentu - wręcz idealne do śledzenia, dlaczego coś poszło nie
tak. Nieudane wykonania możesz też ponowić (**Retry**).

### Webhook: tryb testowy vs produkcyjny

Webhook ma **dwa URL-e**. **Test URL** działa po kliknięciu **Listen for test event** - n8n
nasłuchuje pojedynczego żądania, żebyś zobaczył jego dane w edytorze. **Production URL**
zaczyna działać dopiero, gdy workflow jest **opublikowany** (przycisk **Publish**). To
najczęstsza pułapka początkujących: testowy URL działał, a "na produkcji" cisza - bo
workflow nie został opublikowany. Druga pułapka: poprawiasz node po publikacji, testujesz
pod Test URL i wszystko gra, a Production URL dalej odpowiada po staremu - bo produkcja
używa opublikowanej wersji, dopóki nie klikniesz **Publish** ponownie.

:::caution[Częsty błąd przy webhookach]
Test URL i Production URL to **różne adresy**. Po przejściu na produkcję skopiuj
produkcyjny URL z node'a Webhook i wpisz go w systemie zewnętrznym oraz upewnij się, że
workflow jest opublikowany, a ostatnie zmiany nie czekają na ponowną publikację. Do odsyłania własnej odpowiedzi na żądanie służy osobny node
**Respond to Webhook**.
:::

## Data Tables - wbudowane tabele danych

Prędzej czy później workflow musi coś _zapamiętać_ między uruchomieniami: które zamówienia
już obsłużył, jaki był ostatni kurs waluty, którym klientom wysłał przypomnienie. Kiedyś
oznaczało to podpięcie zewnętrznego arkusza albo bazy. Dziś n8n ma do tego własne
**Data Tables** - proste tabele (wiersze i kolumny) przechowywane w bazie Twojej instancji,
bez żadnych credentials i bez zewnętrznego konta.

Tabele żyją w obrębie **projektu**: znajdziesz je w zakładce **Data tables** obok listy
workflow. Tworzysz je od zera (kolumny definiujesz ręcznie) albo importem pliku CSV, który
sam ustawia strukturę kolumn. W tym samym widoku edytujesz wiersze jak w arkuszu, zmieniasz
kolumny i pobierasz całą tabelę jako CSV.

{/* TODO-MEDIA: zrzut zakładki Data tables w projekcie - lista tabel i otwarta tabela z kilkoma wierszami, widoczny przycisk tworzenia tabeli */}

### Node Data Table - operacje

W workflow z tabelami pracujesz node'em **Data Table**. Najważniejsze operacje na wierszach:

- **Insert** - dopisuje nowe wiersze.
- **Get** - pobiera wiersze pasujące do filtrów.
- **Update** i **Delete** - zmieniają lub usuwają wiersze pasujące do filtrów.
- **Upsert** - aktualizuje wiersz, jeśli istnieje, a w przeciwnym razie go tworzy.
- **If Row Exists** / **If Row Does Not Exist** - przepuszczają dalej tylko te itemy, które
  już są w tabeli (albo których jeszcze nie ma). To gotowy klocek do deduplikacji.

Node ma też operacje na samych tabelach (utworzenie, lista, zmiana, usunięcie), przydatne,
gdy tabele mają powstawać automatycznie. Pełny opis:
[Data Table node (docs.n8n.io)](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable/).

  caption="Typowy wzorzec: powiadom tylko o nowych rzeczach, a obsłużone zapisz w tabeli, żeby przy następnym uruchomieniu ich nie powtarzać."

### Dostępność i limity

- **Od kiedy:** Data Tables weszły w n8n 1.113 (wrzesień 2025) jako beta dla wszystkich
  planów - n8n Cloud i self-hosted
  ([ogłoszenie na forum n8n](https://community.n8n.io/t/data-tables-are-here/192256)).
  Jeśli nie widzisz zakładki Data tables, najpierw zaktualizuj instancję.
- **Limit miejsca:** domyślnie wszystkie tabele w instancji mają **łącznie 200 MiB**
  (stan na listopad 2026). Przy 80% n8n ostrzega, a po dobiciu do limitu zapisy z workflow
  zaczynają kończyć się błędem. Na starcie funkcji limit wynosił 50 MB, więc w starszych
  materiałach spotkasz tę liczbę.
- **Self-hosted:** limit zmienisz zmienną środowiskową `N8N_DATA_TABLES_MAX_SIZE_BYTES`
  (zmienne środowiskowe omawiałem w [Module 1](/modul-1-instalacja-hosting)). Na n8n Cloud
  tej zmiennej nie ustawisz.
- **Widoczność:** tabele w projekcie widzą domyślnie wszyscy członkowie projektu, a Owner
  i Admin instancji - wszystkie tabele.
- **Code node:** nie ma wbudowanego dostępu do tabel. Odczyt i zapis robisz node'em
  Data Table, a wynik przekazujesz do Code node'a jako zwykłe itemy.

Źródło limitów i zasad widoczności:
[Data tables (docs.n8n.io)](https://docs.n8n.io/build/work-with-data/data-tables/).

### Data Tables czy Google Sheets?

| Kryterium | Data Tables | Google Sheets |
| --- | --- | --- |
| Gdzie leżą dane | W bazie Twojej instancji n8n | Na koncie Google |
| Credentials | Niepotrzebne | Konto Google podpięte przez OAuth2 |
| Kto ma dostęp | Członkowie projektu w n8n | Każdy, komu udostępnisz arkusz |
| Ograniczenia | Wspólny limit miejsca na instancję | [Limity zapytań Google Sheets API](https://developers.google.com/workspace/sheets/api/limits) |
| Najlepsze do | Stanu workflow, deduplikacji, cache'u, tabel konfiguracyjnych | Danych, które ogląda lub edytuje człowiek spoza n8n |

Moja zasada: jeśli tabela jest "wewnętrzną pamięcią" automatyzacji i nikt poza n8n do niej
nie zagląda - Data Tables. Jeśli to raport dla szefa albo lista, którą handlowiec poprawia
ręcznie - Google Sheets.

:::caution[Kiedy Data Tables to za mało]
Data Tables są do lekkiego i średniego przechowywania. Gdy danych przybywa w setkach
tysięcy wierszy, potrzebujesz relacji między tabelami, złożonych zapytań SQL albo osobnego
backupu krytycznych danych biznesowych - postaw prawdziwą bazę (np. PostgreSQL) i łącz się
z nią node'em bazy danych. Jeśli Twój backup to eksport workflow do JSON (jak w gotowcu
[Backup workflow do GitHuba](/workflow-backup-n8n-github)), zawartość tabel do niego nie
trafia - ważne tabele co jakiś czas pobieraj jako CSV.
:::

## Organizacja pracy - dobre praktyki od początku

Jeden workflow ogarniesz z pamięci. Dwadzieścia - już nie. Im wcześniej wprowadzisz
porządek, tym mniej czasu stracisz później na szukanie "tego przepływu, który coś robił z
fakturami".

### Projekty i foldery

n8n porządkuje pracę na dwóch poziomach. **Projekt** grupuje workflow, credentials i Data
Tables oraz decyduje, kto ma do nich dostęp i z jaką rolą. Wewnątrz projektu układasz
workflow w **folderach**, także zagnieżdżonych - jak pliki w katalogach.

- **Dostępność:** projekty i role (RBAC) są na wszystkich planach n8n Cloud, a liczba
  projektów zależy od planu. Na self-hostingu dokumentacja n8n sama sobie przeczy: strona
  [Projects](https://docs.n8n.io/administer/manage-users-and-access/set-permissions-and-roles-rbac/organize-work-in-projects/)
  podaje Registered Community (darmowa rejestracja instancji kluczem licencyjnym) wzwyż, a
  [porównanie edycji](https://docs.n8n.io/deploy/host-n8n/community-edition-features)
  wymienia projekty wśród funkcji Business i Enterprise - rejestracja odblokowuje według niego
  foldery, debug in editor i custom execution data (stan na listopad 2026). Co masz u siebie,
  sprawdzisz w **Settings → Plan & usage**.
- **Foldery** weszły w n8n 1.85 (kwiecień 2025) i według ogłoszenia wymagają Registered
  Community Edition lub planu płatnego
  ([ogłoszenie na forum n8n](https://community.n8n.io/t/organize-your-workspace-with-folders/95887)).
- **Przenoszenie** workflow do innego projektu usuwa jego dotychczasowe udostępnienia -
  po przeniesieniu sprawdź, kto ma dostęp.

Mój układ na start: jeden projekt na klienta lub obszar (np. "Marketing", "Finanse"),
a w nim foldery według procesu. Workflow testowe trzymam w osobnym folderze "_sandbox", żeby
nie mieszały się z produkcyjnymi.

### Grupy node'ów na kanwie

Gdy workflow rośnie do kilkudziesięciu node'ów, sticky notes przestają wystarczać. Wtedy
zaznacz powiązane node'y i naciśnij `Ctrl + G` (`Cmd + G` na macOS) - powstanie nazwana
**grupa** (canvas group), którą możesz zwinąć do jednego kafelka i opisać krótkim tekstem.
Grupa zapisuje się razem z workflow. Do grupy nie wejdzie trigger, a minimum to dwa
elementy. Funkcja jest dostępna na wszystkich instancjach od n8n 2.31
([Canvas groups, docs.n8n.io](https://docs.n8n.io/build/understand-workflows/workflow-components/canvas-groups/)).

## Ćwiczenie: pogoda z wttr.in

Czas na pierwsze ćwiczenie, które robisz sam, od pustej kanwy. To "Hello World" automatyzacji:
trzy node'y, zero credentials, a na końcu zdanie zbudowane z danych z prawdziwego API.

- **Cel:** zbudować workflow **Manual Trigger → HTTP Request → Edit Fields**, który pobiera
  bieżącą pogodę dla wybranego miasta z darmowego serwisu [wttr.in](https://wttr.in/) i składa
  z niej jedno zdanie.
- **Czas:** 15-20 minut.
- **Potrzebujesz:** dowolnej instancji n8n (Cloud albo self-hosted z
  [Modułu 1](/modul-1-instalacja-hosting)). Konto ani klucz API do wttr.in nie są potrzebne.

<Flow
  title="cwiczenie-pogoda"
  alt="Schemat ćwiczenia: Manual Trigger uruchamia HTTP Request, który pobiera pogodę z wttr.in, a Edit Fields składa z odpowiedzi jedno zdanie"
  caption="Trzy node'y: ręczny start, pobranie JSON-a z wttr.in i złożenie zdania z wybranych pól."
  spec={`
    Manual Trigger (start ręczny):hand-pointer @green -> HTTP Request (GET wttr.in):globe @blue
    HTTP Request -> Edit Fields (zdanie o pogodzie):pen-to-square @amber
  `}
/>

### Kroki

1. **Nowy workflow i trigger.** Utwórz nowy workflow, kliknij **Add first step** i wybierz
   _Trigger manually_. Na kanwie pojawi się Manual Trigger (podpisany "When clicking
   'Execute workflow'").
2. **HTTP Request.** Dodaj za triggerem node **HTTP Request**: metoda `GET`, URL
   `https://wttr.in/Warszawa?format=j1&lang=pl`. Miasto wpisz bez polskich znaków (`Krakow`,
   `Gdansk`, `Jelenia+Gora`) - spację zastępujesz plusem.
3. **Wymuś format JSON.** W tym samym node'zie kliknij **Add Option → Response** i ustaw
   _Response Format_ na **JSON**. To ważne: wttr.in odsyła JSON z nagłówkiem
   `Content-Type: text/plain`, więc domyślne _Autodetect_ potraktuje odpowiedź jak zwykły
   tekst i dostaniesz jeden długi napis zamiast drzewa pól (nagłówek sprawdziłem `curl`-em
   w listopadzie 2026, opcje _Response Format_ opisuje
   [dokumentacja HTTP Request](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest/)).
4. **Uruchom tylko ten krok.** Kliknij **Execute step** w HTTP Request i obejrzyj Output
   w widoku _Schema_. Znajdziesz tam m.in. `current_condition` (pomiar teraz), `nearest_area`
   (najbliższy punkt pomiarowy) i `weather` (prognoza na trzy dni). Przypnij ten wynik
   klawiszem `P` - kolejne testy nie będą już odpytywać serwisu.
5. **Edit Fields.** Dodaj node **Edit Fields (Set)** w trybie _Manual Mapping_ i utwórz dwa
   pola:
   - `temperatura` typu _Number_ z wartością `{{ $json.current_condition[0].temp_C }}`,
   - `podsumowanie` typu _String_ z wartością
     `{{ $json.nearest_area[0].areaName[0].value }}: {{ $json.current_condition[0].temp_C }}°C, odczuwalna {{ $json.current_condition[0].FeelsLikeC }}°C, {{ $json.current_condition[0].lang_pl[0].value }}`.

   Pole wartości musi być w trybie wyrażeń (_Expression_) - wpisz `=` w pustym polu albo
   po prostu przeciągnij pole z panelu Input, a n8n sam przełączy tryb i zbuduje wyrażenie.
6. **Uruchom całość.** Kliknij **Execute workflow** (`Ctrl + Enter`). Ten workflow zostaje
   testowy - z Manual Triggerem nie ma czego publikować.

<details>
<summary>Sprawdź, czy działa</summary>

- Wszystkie trzy node'y mają zielony znacznik, a na połączeniach widać "1 item".
- Output node'a Edit Fields zawiera dwa pola: `temperatura` jako liczbę (bez cudzysłowu
  w widoku JSON) i `podsumowanie` w stylu `Powisle: 6°C, odczuwalna 4°C, Słonecznie`.
- Gdy podmienisz w URL-u miasto i uruchomisz workflow ponownie (po zdjęciu pinu), zmienia się
  tylko treść pól - reszty workflow nie ruszasz.
- Nazwa w `nearest_area` to najbliższy punkt pomiarowy, nie zawsze nazwa miasta: dla
  Warszawy wttr.in zwraca dzielnicę (Powisle). To nie błąd, tylko kształt danych - dokładnie
  ten rodzaj niespodzianki, który wyłapujesz w panelu Output.

</details>

### Wariant dla zaawansowanych

Dodaj za Edit Fields node **IF** z warunkiem _Number → is greater than_: `{{ $json.temperatura }}`
większe od `15`. Na wyjście _true_ podepnij Edit Fields z polem `rada` = "Kurtka zostaje w domu",
na _false_ - "Weź kurtkę". Logikę IF omawiam szerzej w
[Module 3](/modul-3-praca-z-danymi#logika-if-switch-filter). Drugi krok: zamień Manual Trigger
na Schedule Trigger (codziennie o 7:00) i opublikuj workflow przyciskiem **Publish** - od teraz
prognoza liczy się sama, a wynik zobaczysz w zakładce Executions.

### Typowe pułapki

| Objaw | Przyczyna |
| --- | --- |
| Output HTTP Request to jedno pole `data` z długim tekstem | _Response Format_ zostało na _Autodetect_, a wttr.in wysyła `text/plain` - ustaw **JSON** (krok 3) |
| W polu wyrażenia widać `[undefined]` albo czerwony komunikat | Literówka w ścieżce albo brak `[0]` - `current_condition`, `areaName` i `lang_pl` to tablice |
| Pogoda jest dla zupełnie innego miejsca, np. Szkocji | Polskie znaki w nazwie miasta - wpisz `Gdansk` zamiast `Gdańsk` |
| Opis pogody jest po angielsku | wttr.in nie ma tłumaczenia dla każdego opisu - przy `lang=pl` czasem zostaje angielski tekst, to normalne |
| IF przepuszcza wszystko na złą gałąź | Porównujesz tekst `"6"` zamiast liczby - pole `temperatura` musi mieć typ _Number_ |
| Wynik się nie zmienia po zmianie miasta | Wynik HTTP Request jest przypięty - zdejmij pin (**Unpin data**) |

## Sprawdź się

Zanim ruszysz dalej, odpowiedz sobie na te pytania - na głos albo w dwóch zdaniach na
kartce. Jeśli przy którymś się zawahasz, wróć do podlinkowanej sekcji.

1. Dlaczego Manual Trigger nigdy nie uruchomi workflow "sam z siebie", nawet jeśli
   opublikujesz workflow - co konkretnie odróżnia go pod tym względem od Schedule
   i Webhooka? Jeśli nie masz pewności -
   [Triggery: Manual, Schedule i Webhook](#triggery-manual-schedule-i-webhook).
2. Kolejny node w Twoim przepływie "nie widzi" pola, którego się spodziewałeś, i się
   wywala. Gdzie w edytorze sprawdzisz, jak naprawdę wygląda output poprzedniego node'a,
   zanim zaczniesz zgadywać? Jeśli nie masz pewności -
   [Podgląd danych między node'ami](#podgląd-danych-między-nodeami).
3. Wracasz po pół roku do workflow, w którym node'y nazywają się "HTTP Request1", "Set1",
   "IF1". Co stracisz, a czego byś nie stracił, gdybyś od razu nadał im opisowe nazwy?
   Jeśli nie masz pewności -
   [Organizacja pracy - dobre praktyki od początku](#organizacja-pracy---dobre-praktyki-od-początku).
4. Wczorajsze, produkcyjne uruchomienie zakończyło się błędem, a Ciebie przy tym nie było.
   Jak teraz sprawdzisz, na którym dokładnie kroku i z jakimi danymi coś poszło nie tak?
   Jeśli nie masz pewności - [Lista i szczegóły executions](#lista-i-szczegóły-executions).
5. Twój workflow co godzinę pobiera nowe zgłoszenia z API i ma powiadamiać na Slacku tylko
   o tych, których jeszcze nie widział. Gdzie zapiszesz "już obsłużone" i jaką operacją
   node'a odfiltrujesz powtórki? A gdyby tę listę miał na bieżąco przeglądać i poprawiać
   handlowiec - co byś zmienił? Jeśli nie masz pewności -
   [Data Tables - wbudowane tabele danych](#data-tables---wbudowane-tabele-danych).
6. Masz zaznaczony node, który pobiera dane z płatnego API. Jakimi trzema klawiszami
   przypniesz jego dane, zmienisz mu nazwę na opisową i dodasz obok notatkę z wyjaśnieniem?
   Jeśli nie masz pewności - [Skróty klawiszowe](#skróty-klawiszowe).
7. API zwraca poprawny JSON, a n8n pokazuje Ci jeden długi napis zamiast drzewa pól. Na który
   nagłówek odpowiedzi spojrzysz i które ustawienie node'a HTTP Request zmienisz? Jeśli nie
   masz pewności - [Ćwiczenie: pogoda z wttr.in](#ćwiczenie-pogoda-z-wttrin).

<details>
<summary>Mini-zadanie: zamień Schedule Trigger na Webhook</summary>

Bazujesz na workflow z tego modułu (Schedule Trigger → HTTP Request → Edit Fields).

1. Usuń Schedule Trigger i dodaj w jego miejsce node **Webhook** (metoda `GET`).
2. Połącz go z istniejącym HTTP Request i Edit Fields - reszta przepływu zostaje bez zmian.
3. Kliknij **Listen for test event** i otwórz Test URL w przeglądarce (albo wywołaj go
   `curl`-em).
4. Sprawdź w panelu Output node'a Edit Fields, że dane przeszły tak samo jak wcześniej.
5. Żeby to zadziałało "na produkcji", pamiętaj o dwóch rzeczach z tego modułu: publikacji
   workflow (**Publish**) i użyciu Production URL zamiast Test URL.

</details>

<Takeaways>
  - Edytor n8n to: kanwa, panel node'ów (N / +), panel parametrów i ustawień node'a, lista workflow i executions.
  - Każdy workflow startuje od triggera; uniwersalny wzorzec to "kiedy → skąd → co z tym zrobić".
  - Manual = testy, Schedule = harmonogram/cron, Webhook = reakcja na zdarzenie z zewnątrz.
  - "Execute workflow" uruchamia całość, "Execute step" tylko jeden node - szybsze poprawki.
  - Pinning danych przyspiesza testy i oszczędza limity API, ale działa tylko w edytorze, nie na produkcji.
  - n8n zapisuje zmiany sam, ale na produkcji działa tylko opublikowana wersja - po każdej poprawce kliknij **Publish** ponownie.
  - Webhook ma osobny Test URL i Production URL; produkcyjny wymaga opublikowanego workflow.
  - Kilka skrótów robi największą różnicę: `N` (panel node'ów), `Ctrl/Cmd + Enter` (uruchom), `Ctrl/Cmd + K` (Command Bar), `P` (pin), `Shift + S` (notatka).
  - Data Tables to wbudowana "pamięć" workflow - do stanu, deduplikacji i cache'u; dane dla ludzi spoza n8n trzymaj w Google Sheets, duże i relacyjne - w prawdziwej bazie.
  - Porządek od początku: projekty i foldery, opisowe nazwy, tagi, sticky notes i grupy node'ów.
  - Gdy API odsyła JSON jako `text/plain`, ustaw w HTTP Request _Response Format_ na **JSON** - ćwiczenie z wttr.in pokazuje to w praktyce.
</Takeaways>
