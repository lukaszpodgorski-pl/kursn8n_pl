Tu n8n pokazuje swoją prawdziwą moc: spinanie aplikacji ze sobą. Nauczysz się używać gotowych
node'ów aplikacji, prawidłowo łączyć konta przez credentials (API key i OAuth2), sięgać po dowolne
API node'em HTTP Request oraz odbierać i wysyłać zdarzenia przez webhooki - z uwzględnieniem
paginacji i limitów zapytań.

## Node'y aplikacji - gotowe integracje

Większość popularnych usług ma w n8n dedykowany node aplikacji (app node). To gotowy "adapter":
zamiast samodzielnie konstruować zapytania HTTP, wybierasz z list rozwijanych, co chcesz zrobić.
Pod spodem node i tak rozmawia z API usługi - ale całą czarną robotę (adresy endpointów, format
danych, nagłówki) ma już zaszytą.

:::note[Po ludzku - API, endpoint, REST]

- **API** - "okienko", przez które jeden program rozmawia z drugim. Aplikacja udostępnia API, żeby
  inne narzędzia (jak n8n) mogły pobierać z niej dane i zlecać akcje.
- **Endpoint** - konkretny adres tego okienka, np. "dodaj kontakt" albo "pobierz zamówienia". Jedno
  API ma zwykle wiele endpointów.
- **REST** - najpopularniejszy styl API: zwykłe adresy URL plus metody HTTP (pobierz, dodaj, zmień,
  usuń). Jeśli usługa ma "REST API", obsłużysz ją node'em HTTP Request.

:::

### Struktura node'a aplikacji: Resource → Operation

Niemal wszystkie node'y aplikacji w n8n działają według tego samego schematu dwóch list:

- **Resource (zasób)** - _co_ obsługujesz w danej usłudze: arkusz, wiadomość, plik, kontakt, rekord, kanał.
- **Operation (operacja)** - _jaką akcję_ wykonujesz na tym zasobie: `Create`, `Get`, `Get Many`, `Update`, `Delete`, `Append` itp.

Przykład: w node Google Sheets wybierasz **Resource:** `Sheet Within Document` i **Operation:**
`Append Row`. W node Slack - **Resource:** `Message` i **Operation:** `Send`. Gdy zapamiętasz ten
wzorzec, nowy node aplikacji obsłużysz w kilka sekund, nawet jeśli widzisz go pierwszy raz.

:::note[Trigger node vs action node]
Wiele aplikacji ma dwie wersje node'a. **Trigger** (np. "Gmail Trigger") _rozpoczyna_ workflow, gdy
w usłudze coś się wydarzy. **Node akcji** (np. "Gmail") _wykonuje coś_ w środku przepływu. W
kanwie szukaj ich oddzielnie - trigger ma w nazwie dopisek "Trigger".
:::

:::tip[Kiedy node aplikacji, a kiedy HTTP Request]
Jeśli usługa ma gotowy node - zacznij od niego. Jest szybszy, czytelniejszy i mniej podatny na
błędy. Po HTTP Request (sekcja 3) sięgaj dopiero, gdy node nie istnieje albo nie wystawia akcji,

## Uwierzytelnianie: API key vs OAuth2

Żeby node mógł działać w Twoim imieniu, musi się zalogować do usługi. W n8n robisz to raz -
zapisując **credentials** (poświadczenia) - a potem wybierasz je w node'ie. Najczęstsze dwa typy to
klucz API oraz OAuth2. Różnią się sposobem, w jaki usługa Cię "rozpoznaje".

### Jak działają credentials w n8n

Credentials to osobny, wielokrotnego użytku obiekt. Tworzysz je w sekcji **Credentials** lub
bezpośrednio z poziomu node'a (pole "Credential to connect with" → "Create New"). Jedne
poświadczenia możesz podpiąć pod wiele node'ów i workflow, a w wersjach zespołowych - udostępnić
innym użytkownikom bez pokazywania im samego sekretu.

#### API key - prosty sekret

Generujesz klucz (token) w panelu usługi i wklejasz go do credentiala w n8n. Przy każdym zapytaniu
n8n dołącza ten klucz - zwykle w nagłówku (np. `Authorization: Bearer …` lub `X-API-Key`) albo w
parametrze zapytania. Prosto, ale klucz działa do odwołania i daje pełen zakres uprawnień, jakie ma
konto.

#### OAuth2 - autoryzacja przez zgodę

Tu nie wklejasz hasła. Klikasz **"Connect my account"**, n8n przekierowuje Cię do usługi, ta pyta
"czy zgadzasz się, by n8n miał dostęp do X?", a po Twojej zgodzie odsyła użytkownika z powrotem na
**adres callback** n8n wraz z kodem. n8n wymienia ten kod na **access token** (krótkożyciowy) i
**refresh token** (do automatycznego odświeżania). Dzięki temu dostęp jest ograniczony do wybranych
_scope'ów_ i można go cofnąć po stronie usługi.

| Cecha | API key | OAuth2 |
| --- | --- | --- |
| Konfiguracja | Wklej klucz - szybko | Klik "Connect", zgoda w przeglądarce |
| Zakres uprawnień | Zwykle pełny (jak konto) | Ograniczony do wybranych scope'ów |
| Wygasanie | Działa do odwołania | Access token krótkożyciowy, odświeżany refresh tokenem |
| Callback / HTTPS | Niepotrzebny | Wymaga adresu callback; część dostawców chce HTTPS, Google dopuszcza `http://localhost` |
| Wycofanie dostępu | Trzeba unieważnić klucz w usłudze | Cofasz zgodę w panelu usługi |
| Typowo używane przez | Notion, Airtable, wiele prostych API | Google, Microsoft, Slack, GitHub |
| Najlepsze do… | Szybki start, własne / wewnętrzne API | Konta użytkowników, ograniczony i odwoływalny dostęp |

### Gdzie n8n trzyma credentials

Poświadczenia są przechowywane w bazie n8n w postaci **zaszyfrowanej**. Do szyfrowania służy
**encryption key** - n8n generuje go przy pierwszym uruchomieniu (lub ustawiasz go zmienną
`N8N_ENCRYPTION_KEY`). Bez tego klucza zaszyfrowane credentials są bezużyteczne, dlatego przy
self-hostingu musisz go zachować i mieć w backupie - inaczej po migracji stracisz dostęp do
wszystkich połączeń.

:::caution[OAuth2 a publiczny adres]
Przepływ OAuth2 odsyła Twoją przeglądarkę na adres callback instancji n8n. Skoro przekierowanie
idzie przez przeglądarkę, `localhost` często wystarczy: Google wymaga `https://` w callbacku, ale
adresy `localhost` są z tej zasady wyłączone
([Google OAuth 2.0](https://developers.google.com/identity/protocols/oauth2/web-server), stan na
listopad 2026). Część dostawców wymaga jednak HTTPS bez wyjątków - sprawdź w ich dokumentacji.
Publiczny adres HTTPS jest konieczny dla webhooków i triggerów (usługa musi do Ciebie
zadzwonić) oraz dla dostępu z innych urządzeń. Jeśli self-hostujesz, zadbaj o domenę,
certyfikat i poprawnie ustawiony `WEBHOOK_URL` - zasady konfiguracji rozkładam w
[Module 1: Instalacja i hosting](/modul-1-instalacja-hosting).
:::

:::tip[Dobre praktyki dla credentials]

- Nadawaj kontom serwisowym **minimalny zakres** uprawnień (zasada najmniejszych przywilejów).
- Nie wklejaj kluczy do pól node'a "na sztywno" - zawsze używaj obiektu credentials.
- Trzymaj `N8N_ENCRYPTION_KEY` w bezpiecznym miejscu i w backupie.
- Regularnie rotuj klucze API i cofaj zgody OAuth, których już nie używasz.

:::

## HTTP Request - uniwersalny klucz do każdego API

Gdy usługa nie ma gotowego node'a (albo node nie wystawia danej akcji), sięgasz po node **HTTP
Request**. To uniwersalny klient HTTP: potrafi odpytać dowolne REST/HTTP API. Jeśli usługa ma
dokumentację API, zwykle da się ją obsłużyć właśnie tym node'em.

### Najważniejsze pola node'a

- **Method** - metoda HTTP: `GET` (pobierz), `POST` (utwórz/wyślij), `PUT`/`PATCH` (aktualizuj), `DELETE` (usuń) i inne.
- **URL** - adres endpointu. Możesz wstawiać dane z poprzednich node'ów wyrażeniami `{{ }}`.
- **Query Parameters** - parametry doklejane do URL po znaku `?` (np. filtry, strony, sortowanie).
- **Headers** - nagłówki, np. `Content-Type`, `Accept`, niestandardowe nagłówki API.
- **Body** - treść żądania dla POST/PUT/PATCH. Do wyboru m.in. `JSON`, `Form-Urlencoded`, `Form-Data` (multipart, np. pliki) czy `Raw`.
- **Authentication** - sposób logowania: _None_, _Predefined Credential Type_ (gotowe credentiale danej usługi) albo _Generic Credential Type_ (Basic / Header / Query / OAuth2). Dzięki temu nie wpisujesz kluczy ręcznie w nagłówki.

### Przykład: POST z body JSON i autoryzacją w nagłówku

```http
POST https://api.przyklad.pl/v1/zadania

Headers:
  Content-Type: application/json
  Accept: application/json
  # Authorization dołączany automatycznie przez credentials

Query Parameters:
  notify=true

Body (JSON):
{
  "tytul": "{{ $json.temat }}",
  "priorytet": "wysoki",
  "przypisany_do": "{{ $json.email }}"
}
```

:::tip[Skróty, które oszczędzają czas]

- **Import cURL** - w node HTTP Request jest opcja "Import cURL". Wklej polecenie `curl` z
  dokumentacji API, a n8n samo uzupełni metodę, URL, nagłówki i body.
- **Wyrażenia w każdym polu** - URL, nagłówki i body możesz budować dynamicznie z danych z
  poprzednich kroków (więcej w [Module 3: Praca z danymi](/modul-3-praca-z-danymi)).
- **Autoryzacja przez credentials** - zamiast wpisywać token w nagłówek, użyj "Generic Credential
  Type → Header Auth". Klucz zostaje zaszyfrowany, a nie widoczny w workflow.

:::

#### Kiedy HTTP Request zamiast gotowego node'a

- Usługa nie ma node'a w n8n (np. niszowe albo wewnętrzne firmowe API).
- Node istnieje, ale brakuje w nim konkretnej operacji lub nowego pola z API.
- Chcesz korzystać z najnowszej wersji API, zanim node zostanie zaktualizowany.
- Potrzebujesz pełnej kontroli nad nagłówkami, body i obsługą paginacji.

## Webhooki: odbieranie i wysyłanie

Webhook to sposób, w jaki systemy mówią sobie nawzajem "właśnie coś się stało" - natychmiast, bez
odpytywania w pętli. W n8n występuje to w dwie strony: **odbierasz** zdarzenia node'em Webhook oraz
**wysyłasz** zdarzenia do cudzego webhooka node'em HTTP Request.

### Odbieranie: node Webhook

Node **Webhook** to trigger - czeka na przychodzące żądanie HTTP pod własnym, publicznym adresem
URL i uruchamia workflow. Najważniejsze ustawienia:

- **HTTP Method** - na jaką metodę nasłuchuje (najczęściej `POST` lub `GET`).
- **Path** - ścieżka tworząca unikalny adres webhooka.
- **Authentication** - zabezpieczenie endpointu (np. Header Auth, Basic Auth), by nie każdy mógł go wywołać.
- **Respond** - kiedy i jak odpowiedzieć wywołującemu: _Immediately_ (od razu), _When Last Node Finishes_ (po zakończeniu workflow) albo _Using 'Respond to Webhook' Node_ (pełna kontrola nad odpowiedzią).

:::caution[Test URL vs Production URL]
Webhook ma **dwa adresy**. **Test URL** działa tylko gdy klikniesz "Listen for test event" w
edytorze - służy do budowania i podglądu danych. **Production URL** działa stale, ale dopiero gdy
workflow jest **opublikowany** (przycisk **Publish** w prawym górnym rogu edytora; w n8n 1.x
był to przełącznik "Active"). Częsty błąd początkujących: wpisanie zewnętrznej usłudze adresu
testowego albo zapomnienie o publikacji workflow. Pamiętaj też, że zmiany wprowadzone po
publikacji trafiają na Production URL dopiero po ponownym kliknięciu **Publish**.
:::

#### Odpowiadanie: node Respond to Webhook

Gdy w node Webhook ustawisz Respond na _Using 'Respond to Webhook' Node_, na końcu workflow dodajesz
node **Respond to Webhook**. Pozwala on zwrócić dokładnie taką odpowiedź, jakiej oczekuje system
wywołujący - m.in. `JSON`, `Text`, dane binarne, przekierowanie (redirect) albo brak treści.
Ustawisz też **kod odpowiedzi** (np. 200, 201, 400) i własne nagłówki. To kluczowe, gdy budujesz
mały endpoint API albo obsługujesz formularz oczekujący konkretnej odpowiedzi.

### Czy to naprawdę Stripe? Weryfikacja podpisu (HMAC)

Production URL webhooka to zwykły publiczny adres. Każdy, kto go pozna, może wysłać na niego
`POST` z JSON-em wyglądającym jak "płatność opłacona" od Stripe albo "nowy push" od GitHuba.
Jeśli Twój workflow na tej podstawie wysyła fakturę albo nadaje dostęp do kursu, musisz najpierw
sprawdzić, czy żądanie naprawdę przyszło od nadawcy i czy nikt nie zmienił treści po drodze.
Służy do tego **podpis HMAC** - i to jest coś innego niż pole Authentication w node Webhook.

#### Authentication w node Webhook a podpis HMAC

Node Webhook ma wbudowane opcje **Authentication**, m.in. _Basic auth_, _Header auth_, _JWT auth_
i _None_ ([dokumentacja node'a Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/),
stan na listopad 2026). Header auth działa świetnie, gdy to Ty konfigurujesz nadawcę - np. własną
aplikację, formularz albo inne n8n - i możesz dopisać do żądania nagłówek ze stałym tokenem.

Duzi dostawcy (Stripe, GitHub, Shopify i podobni) zwykle nie dają Ci dopisać własnego nagłówka.
Zamiast tego **podpisują** każde żądanie wspólnym sekretem, który dostajesz przy zakładaniu
webhooka w ich panelu. Różnica jest zasadnicza:

| | Header auth (stały token) | Podpis HMAC |
| --- | --- | --- |
| Co leci w żądaniu | Sam sekret, przy każdym wywołaniu | Tylko podpis - sekret nigdy nie opuszcza nadawcy |
| Wyciek jednego żądania | Atakujący ma token i wyśle dowolną treść | Atakujący ma podpis tylko tej jednej treści |
| Ochrona treści | Brak - body można podmienić | Każda zmiana body psuje podpis |
| Gdzie sprawdzasz | n8n robi to sam (pole Authentication) | Ty, w workflow (Crypto + Code) |

#### Jak działa podpis

**HMAC** (Hash-based Message Authentication Code) to skrót kryptograficzny liczony z dwóch
składników naraz: treści wiadomości i sekretu. Nadawca liczy HMAC z **surowego body** żądania
(dokładnie tych bajtów, które wysyła; niektórzy, jak Stripe, doklejają przed nim znacznik
czasu) i dokleja wynik w nagłówku. Ty liczysz to samo po swojej
stronie tym samym sekretem i porównujesz. Zgodność oznacza, że nadawca zna sekret i że body
dotarło bez zmian.

Na przykładzie GitHuba: podpis przychodzi w nagłówku `X-Hub-Signature-256`, to HMAC-SHA256
w zapisie szesnastkowym (hex) z prefiksem `sha256=`
([dokumentacja GitHuba o walidacji dostaw webhooków](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries),
stan na listopad 2026). Stripe używa nagłówka `Stripe-Signature` w formacie `t=...,v1=...`, czyli
podpis plus znacznik czasu
([dokumentacja Stripe o błędach weryfikacji podpisu](https://docs.stripe.com/webhooks/signature),
stan na listopad 2026). Nazwa nagłówka, format i to, co dokładnie jest podpisane, zmieniają się
między dostawcami - zasada zostaje ta sama. Przepis niżej jest dla GitHuba, wariant dla Stripe
znajdziesz zaraz po nim.

:::caution[Podpisane jest surowe body, nie JSON po parsowaniu]
Node Webhook domyślnie parsuje JSON do `$json.body`. Jeśli zamienisz go z powrotem na tekst
(`JSON.stringify`), dostaniesz inne bajty - inne spacje, czasem inną kolejność - i podpis się nie
zgodzi, choć dane są prawdziwe. HMAC licz zawsze z surowej treści żądania.
:::

#### Realizacja w n8n: Webhook, Crypto, Code

<Flow
  title="webhook-hmac"
  alt="Diagram: Webhook z opcją Raw Body odbiera żądanie, node Crypto liczy HMAC z surowego body, Code porównuje podpisy, If przepuszcza żądanie z poprawnym podpisem do dalszej logiki, a z błędnym odsyła 401"
  caption="Podpis sprawdzasz na samym początku workflow - zanim cokolwiek zrobisz z danymi."
  spec={`
    Webhook (Raw Body włączone):satellite-dish @pink -> Crypto (Hmac SHA256, HEX):fingerprint @violet
    Crypto -> Code (porównaj podpisy):code @blue
    Code -> If (podpis OK?):code-branch @amber
    If -tak-> Logika workflow:gears @green
    If -nie-> Respond 401:ban @red

/>

1. **Webhook** - w _Options_ włącz **Raw Body**. Node dalej oddaje sparsowane `body` w JSON-ie,
   ale dodatkowo zapisuje surową treść żądania jako dane binarne pod nazwą `data`
   (tak działa kod node'a w [repozytorium n8n](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Webhook/Webhook.node.ts),
   stan na listopad 2026). Respond ustaw na _Using 'Respond to Webhook' Node_, żeby móc odesłać 401.
2. **Crypto** - akcja **Hmac**: włącz _Binary File_, _Binary Property Name_ `data`, _Type_ `SHA256`,
   _Encoding_ `HEX`, _Property Name_ np. `expected`. Sekret od dostawcy wpisujesz w credentialu
   Crypto, w polu **Hmac Secret** - jest zaszyfrowany jak każde credentials, a nie widoczny w workflow
   ([dokumentacja node'a Crypto](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.crypto/),
   stan na listopad 2026).
3. **Code** (tryb _Run Once for Each Item_) - porównuje podpis z nagłówka z wyliczonym, w sposób
   odporny na timing (kod niżej).
4. **If** na polu `signatureValid` - gałąź _true_ prowadzi do właściwej logiki, gałąź _false_ do
   **Respond to Webhook** z kodem `401` i do niczego więcej.

```js
// Code node, tryb "Run Once for Each Item"
// Wejście: item z node'a Crypto (nagłówki z Webhooka + pole "expected")
const crypto = require('crypto');

// 1. Podpis od nadawcy. n8n zapisuje nazwy nagłówków małymi literami.
//    GitHub: "sha256=<hex>". Brak nagłówka = pusty tekst = podpis odrzucony.
const received = String($json.headers['x-hub-signature-256'] || '');

// 2. Podpis policzony przez node Crypto z surowego body (HEX) + prefiks GitHuba
const expected = 'sha256=' + $json.expected;

const a = Buffer.from(received, 'utf8');
const b = Buffer.from(expected, 'utf8');

// 3. Porównanie w stałym czasie. timingSafeEqual rzuca wyjątek przy buforach
//    różnej długości, więc długość sprawdzamy najpierw.
const valid = a.length === b.length && crypto.timingSafeEqual(a, b);

return { json: { ...$json, signatureValid: valid } };
```

Dlaczego nie zwykłe `received === expected`? Porównanie tekstów kończy się na pierwszym
różniącym się znaku, więc czas odpowiedzi zdradza, ile początkowych znaków atakujący trafił.
`crypto.timingSafeEqual` sprawdza zawsze wszystkie bajty - tego wymaga też dokumentacja GitHuba.

#### Wariant dla Stripe: podpis ze znacznikiem czasu

Przepis wyżej jest dla GitHuba, który podpisuje samo body. **Stripe podpisuje coś innego:**
znacznik czasu, kropkę i dopiero body (`t + "." + body`), a nagłówek `Stripe-Signature` ma postać
`t=1731150000,v1=<hex>`. Policzony samym Crypto z body podpis nigdy się nie zgodzi i każde
prawdziwe zdarzenie dostanie 401 ([Stripe - ręczna weryfikacja podpisu](https://docs.stripe.com/webhooks#verify-manually),
stan na listopad 2026). Układ zostaje ten sam, dochodzi jeden Code przed Crypto:

1. **Code "Przygotuj podpis"** (tryb _Run Once for All Items_) - rozbiera nagłówek na `t` i `v1`
   i składa tekst do podpisania z surowego body (kod niżej).
2. **Crypto** - akcja **Hmac**, ale tym razem _Binary File_ wyłączone, _Value_
   `{{ $json.signedPayload }}`, _Type_ `SHA256`, _Encoding_ `HEX`, _Property Name_ `expected`.
   Sekret (`whsec_...`) dalej w credentialu Crypto.
3. **Code "Porównaj"** - jak dla GitHuba, ale porównujesz `expected` z `v1` (bez prefiksu)
   i dodatkowo odrzucasz zdarzenia starsze niż 5 minut - tyle domyślnie toleruje Stripe.

```js
// Code "Przygotuj podpis", tryb "Run Once for All Items"
const out = [];
for (let i = 0; i < $input.all().length; i++) {
  const item = $input.all()[i];
  // "t=1731150000,v1=abc...,v0=..." -> { t: "1731150000", v1: "abc..." }
  const parts = Object.fromEntries(
    String(item.json.headers['stripe-signature'] || '')
      .split(',')
      .map((p) => p.split('='))
  );
  // Surowe bajty body z opcji Raw Body (binarne "data")
  const raw = await this.helpers.getBinaryDataBuffer(i, 'data');
  out.push({
    json: {
      ...item.json,
      t: parts.t || '',
      v1: parts.v1 || '',
      signedPayload: `${parts.t}.${raw.toString('utf8')}`,
    },
  });
}
return out;
```

```js
// Code "Porównaj" (Stripe), tryb "Run Once for Each Item"
const crypto = require('crypto');
const a = Buffer.from(String($json.v1), 'utf8');
const b = Buffer.from(String($json.expected), 'utf8');
const podpisOk = a.length === b.length && crypto.timingSafeEqual(a, b);
// Znacznik czasu w sekundach; starsze niż 300 s odrzucamy (ochrona przed powtórką)
const wiek = Math.abs(Date.now() / 1000 - Number($json.t));
return { json: { ...$json, signatureValid: podpisOk && wiek <= 300 } };
```

`getBinaryDataBuffer` to oficjalny sposób na dostęp do danych binarnych w Code node
([Get the binary data buffer](https://docs.n8n.io/build/code-in-n8n/cookbook/code-node/get-the-binary-data-buffer)). Z tego samego powodu co wcześniej nie składaj
`signedPayload` z `JSON.stringify($json.body)`.

:::note[Moduł crypto w Code node]
W n8n Cloud moduł `crypto` jest dostępny w Code node od ręki
([dokumentacja Code node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.code/),
stan na listopad 2026). Na self-hostingu import modułów jest domyślnie wyłączony - dopuść go
zmienną `NODE_FUNCTION_ALLOW_BUILTIN=crypto`
([włączanie modułów w Code node](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/enable-modules-in-code-node)).
Gdzie ją wpisać, zależy od trybu task runnerów. W trybie internal ustawiasz ją jako zmienną
środowiskową kontenera n8n. W trybie external (osobny kontener `n8nio/runners`) wpisujesz ją
jako `env-override` w pliku `/etc/n8n-task-runners.json` - dopisana do `environment:` kontenera
nie zadziała i `require('crypto')` dalej będzie odrzucany
([Task runners environment variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/task-runners)).
Więcej o modułach w [Module 5: Kod i sub-workflow](/modul-5-kod-sub-workflow).
:::

#### Ochrona przed powtórką (replay)

Poprawny podpis nie zabezpiecza przed jednym: ktoś przechwytuje prawdziwe, podpisane żądanie
i wysyła je ponownie za godzinę. Podpis dalej się zgadza, bo body jest to samo. Bronisz się na
dwa sposoby, najlepiej łącznie:

- **Znacznik czasu w podpisie** - jeśli dostawca go podpisuje (jak `t=` w nagłówku Stripe),
  odrzucaj żądania starsze niż kilka minut. Czas jest objęty podpisem, więc nie da się go podmienić.
- **Identyfikator zdarzenia** - każde zdarzenie ma unikalne ID. Node **Remove Duplicates**
  z operacją _Remove Items Processed in Previous Executions_ odsiewa ID widziane w poprzednich
  wykonaniach ([dokumentacja Remove Duplicates](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.removeduplicates/),
  stan na listopad 2026). To chroni też przed zwykłymi ponowieniami - dostawcy wysyłają to samo
  zdarzenie drugi raz, gdy nie dostaną szybko odpowiedzi 2xx.

:::tip[Sekret traktuj jak hasło]
Sekret webhooka trzymaj wyłącznie w credentialu, nigdy wpisany w kod Code node'a. Rotuj go
w panelu dostawcy, gdy podejrzewasz wyciek - Stripe pozwala do 24 godzin utrzymać stary
i nowy sekret równolegle, żebyś zdążył podmienić credential bez przerwy w działaniu.
:::

### Wysyłanie zdarzeń do cudzego webhooka

Druga strona medalu: to _Ty_ powiadamiasz inny system. Nie ma do tego osobnego node'a - używasz
**HTTP Request** (sekcja 3), kierując `POST` na adres webhooka odbiorcy (np. Slack Incoming
Webhook, Discord, własna aplikacja).

1. **Zdobądź adres webhooka odbiorcy** - Skopiuj URL z panelu usługi docelowej (np. "Incoming Webhook" w Slacku) - to adres, na który wyślesz żądanie.
2. **Dodaj node HTTP Request** - Ustaw **Method: POST** i wklej skopiowany URL w pole adresu.
3. **Zbuduj body w formacie odbiorcy** - Wybierz Body → JSON i przygotuj strukturę, jakiej oczekuje usługa (np. `{ "text": "{{ $json.wiadomosc }}" }` dla Slacka).
4. **Przetestuj i podłącz do triggera** - Uruchom node, sprawdź odpowiedź (kod 200/204), a potem podepnij go za właściwym triggerem, by zdarzenie wysyłało się automatycznie.

:::note[Webhook (odbiór) vs Polling (odpytywanie)]
Webhook reaguje natychmiast i nie obciąża API zbędnymi zapytaniami - usługa sama puka, gdy coś się
wydarzy. Polling (trigger sprawdzający co X minut) używasz, gdy usługa _nie_ oferuje webhooków.
Jeśli masz wybór, webhook jest zwykle szybszy i tańszy w wykonaniach.
:::

## Paginacja, limity zapytań i ponawianie

Prawdziwe API rzadko oddają wszystko naraz. Wyniki dzielą na strony, narzucają limity liczby
zapytań i bywają chwilowo niedostępne. Solidna integracja musi to obsłużyć - inaczej pobierzesz
tylko pierwszą stronę albo dostaniesz błąd `429`.

### Paginacja - pobieranie wielu stron

Gdy lista wyników jest długa, API zwraca ją w kawałkach (stronach). Trzeba odpytać kolejne strony,
aż skończą się dane. Najczęstsze schematy:

- **Offset / limit** - przesuwasz wskaźnik startu (`?offset=100&limit=100`) aż przestaną wracać wyniki.
- **Page / per_page** - zwiększasz numer strony (`?page=2`), aż dostaniesz pustą stronę.
- **Cursor / next token** - odpowiedź zawiera "wskaźnik" do następnej porcji (`nextCursor`), który przekazujesz w kolejnym żądaniu, aż przestanie przychodzić.

W node **HTTP Request** nie musisz budować pętli ręcznie - w opcjach jest **Pagination**.
Ustawiasz w niej tryb (np. "Update a Parameter in Each Request" lub "Response Contains Next URL"),
warunek zakończenia oraz parametr/wartość pobieraną z poprzedniej odpowiedzi. Node sam dopytuje
kolejne strony i scala wyniki. Gotowe node'y aplikacji często mają to jeszcze prościej - przełącznik
`Return All` zamiast ręcznego limitu.

:::caution[Uważaj na rate limity (limity zapytań)]
Niemal każde API ogranicza liczbę zapytań na sekundę/minutę. Przekroczenie zwraca kod **HTTP 429
"Too Many Requests"**. Pętla paginacji albo przetwarzanie dużej listy itemów potrafią błyskawicznie
wyczerpać limit. Zanim zbudujesz integrację na produkcję, sprawdź w dokumentacji API, jaki jest
limit i jak długo trwa "blokada".
:::

### Ponawianie, opóźnienia i batchowanie

Gdy trafisz na limit lub chwilową awarię, n8n daje kilka mechanizmów, by sobie z tym poradzić:

<CardGrid>
  <ConceptCard icon="fa-rotate-right" title="Retry On Fail">
    W ustawieniach node'a (Settings) włączasz automatyczne ponawianie po błędzie - z liczbą prób i
    odstępem między nimi. Idealne przy `429` i krótkich awariach.
  </ConceptCard>
  <ConceptCard icon="fa-layer-group" title="Batchowanie">
    Node **Loop Over Items** (Split in Batches) dzieli listę na mniejsze paczki, byś nie wysyłał
    setek zapytań naraz i mieścił się w limicie.
  </ConceptCard>
  <ConceptCard icon="fa-hourglass-half" title="Opóźnienia">
    Node **Wait** dodaje pauzę między partiami zapytań - rozkłada ruch w czasie, by nie uderzać w
    API zbyt gęsto.
  </ConceptCard>
  <ConceptCard icon="fa-gauge-high" title="Batch interval w HTTP Request">
    W opcjach node'a HTTP Request ustawisz wielkość partii i odstęp (batching), by samodzielnie
    spowolnić serię żądań.
  </ConceptCard>
</CardGrid>

:::tip[Przepis na odporną integrację]
Łącz mechanizmy: **paginacja** pobiera komplet danych, **Loop Over Items + Wait** rozkłada zapytania
w czasie, a **Retry On Fail** łapie sporadyczne błędy. Taki workflow przetrwa chwilowe limity i nie
zgubi danych po drodze. Obsługę błędów na poważnie (Error Trigger, Stop and Error) rozwijamy w
[Module 7: Produkcja](/modul-7-produkcja).
:::

## Ćwiczenie: berek na webhookach

Webhooki najlepiej zrozumieć, kiedy jeden workflow "klepie" drugi. Zbudujesz dwa: **Odbiornik**,
który czeka na wiadomość pod Production URL, i **Nadajnik**, który ją wysyła node'em HTTP
Request. Najlepiej gra się w parze - Twój Nadajnik klepie Odbiornik kolegi na jego instancji,
a jego Nadajnik Twój. Jeśli masz jedną instancję i nikogo pod ręką, oba workflow postawisz
u siebie - wariant poniżej.

- **Cel:** wysłać wiadomość JSON z jednego workflow i odebrać ją w drugim przez Production URL
  opublikowanego webhooka.
- **Czas:** 25-35 minut.
- **Potrzebujesz:** jednej instancji n8n (wariant solo) albo dwóch instancji osiągalnych przez
  sieć (wariant w parze). Instancja na `localhost` wystarczy do gry solo, ale do gry w parze
  musi mieć publiczny adres HTTPS i ustawione `WEBHOOK_URL` - patrz
  [HTTPS, domena, reverse proxy i Cloudflare Tunnel](/modul-1-instalacja-hosting#https-domena-reverse-proxy-i-cloudflare-tunnel).
  n8n Cloud ma publiczny adres od razu.

### Kroki

1. **Odbiornik: webhook.** Utwórz workflow "Berek - Odbiornik" z node'em **Webhook**:
   _HTTP Method_ `POST`, _Path_ `berek-twoje-imie` (bez polskich znaków), _Respond_
   _Immediately_. Authentication na razie zostaw na _None_.
2. **Odbiornik: co przyszło.** Za Webhookiem dodaj **Edit Fields** z polami `od` =
   `{{ $json.body.from }}`, `wiadomosc` = `{{ $json.body.message }}` i `odebrano` =
   `{{ $now.toISO() }}`. Webhook podaje treść żądania w polu `body`, obok `headers` i `query` -
   stąd `$json.body.from`, a nie samo `$json.from`.
3. **Odbiornik: publikacja.** Kliknij **Publish** (`Shift + P`). Otwórz node Webhook, przełącz
   widok adresu na **Production URL** i skopiuj go. Gracie w parze - wyślij adres koledze.
4. **Nadajnik: wiadomość.** Utwórz drugi workflow "Berek - Nadajnik": **Manual Trigger** →
   **HTTP Request** z metodą `POST` i URL-em Odbiornika (Twojego w wariancie solo, kolegi
   w wariancie w parze). Włącz _Send Body_, _Body Content Type_ ustaw na **JSON**, a w
   _Specify Body_ wybierz _Using Fields Below_ i dodaj trzy pola: `from` (Twoje imię),
   `message` (dowolne zaczepienie, np. "Berek! Gonisz") i `sent_at` = `{{ $now.toISO() }}`.
5. **Klep.** Uruchom Nadajnik (**Execute workflow**). Nadajnik możesz zostawić
   nieopublikowany - Manual Trigger i tak działa tylko z edytora.
6. **Sprawdź u odbiorcy.** Otwórz Odbiornik, zakładkę **Executions**, i kliknij najnowsze
   wykonanie.

<details>
<summary>Sprawdź, czy działa</summary>

- Output HTTP Request w Nadajniku to krótki komunikat w stylu
  `{ "message": "Workflow was started" }` - tak od razu odpowiada webhook ustawiony na
  _Respond Immediately_ (dokładne brzmienie bywa różne w zależności od wersji n8n).
- W Executions Odbiornika jest nowe wykonanie ze statusem **Success**, uruchomione
  produkcyjnie (nie z edytora) - nie klikałeś niczego w Odbiorniku, a jednak ruszył.
- Edit Fields w tym wykonaniu pokazuje `od`, `wiadomosc` i `odebrano` z danymi, które wysłał
  Nadajnik. W wariancie w parze: wiadomość, której sam nie pisałeś.
- W danych node'a Webhook widzisz też `headers` - m.in. `user-agent` i adres hosta. Tak
  wygląda każde żądanie, które przychodzi do n8n z zewnątrz.

</details>

### Wariant dla zaawansowanych

- **Zabezpiecz Odbiornik.** W node Webhook ustaw _Authentication_ na **Header Auth** i utwórz
  credential z nagłówkiem, np. `X-Berek-Token`, i długim losowym sekretem. Nadajnik bez tego
  nagłówka powinien dostać odmowę - dopiero gdy w HTTP Request ustawisz _Authentication_ →
  _Generic Credential Type_ → **Header Auth** z tym samym sekretem, berek wraca do gry. Pamiętaj
  o ponownym **Publish** Odbiornika po zmianie. Kiedy Header Auth to za mało, przeczytasz
  w sekcji o [podpisie HMAC](#czy-to-naprawdę-stripe-weryfikacja-podpisu-hmac).
- **Odbij piłeczkę.** Przestaw _Respond_ na _Using 'Respond to Webhook' Node_, dodaj na końcu
  Odbiornika **Respond to Webhook** z JSON-em `{ "odpowiedz": "Mam Cię! Teraz Ty gonisz" }`
  i opublikuj ponownie. Nadajnik zobaczy w Output tę odpowiedź zamiast domyślnego komunikatu o starcie workflow.

### Typowe pułapki

| Objaw | Przyczyna |
| --- | --- |
| 404 z komunikatem, że webhook _is not registered_ | Odbiornik nie jest opublikowany albo Nadajnik używa Test URL zamiast Production URL |
| 404 z podpowiedzią _Did you mean to make a … request?_ | Niezgodna metoda - Webhook nasłuchuje na `POST`, a HTTP Request wysyła `GET` (albo odwrotnie) |
| W Odbiorniku pola `od` i `wiadomosc` są puste | Wyrażenie bez `body` - dane leżą w `$json.body.from`, a nie w `$json.from` |
| Kolega dostaje `ECONNREFUSED` albo timeout | Wysłałeś mu adres z `localhost` - Twoja instancja nie ma publicznego adresu albo brakuje `WEBHOOK_URL` |
| Publikacja Odbiornika kończy się błędem o zajętej ścieżce | Inny opublikowany workflow ma już ten sam _Path_ i metodę - zmień ścieżkę |
| Odbiornik po poprawkach dalej działa po staremu | Produkcja używa opublikowanej wersji - po każdej zmianie kliknij **Publish** ponownie |
| Odmowa (401 lub 403) po włączeniu Header Auth | Nazwa albo wartość nagłówka w Nadajniku różni się od tej w credentialu Odbiornika |

<summary>Mini-zadanie: zbuduj mały endpoint webhookiem</summary>

Potrzebujesz działającej instancji n8n i kilkunastu minut.

1. Dodaj node **Webhook** - metoda `GET`, dowolny `Path` (np. `status`), a w polu
   **Respond** wybierz _Using 'Respond to Webhook' Node_.
2. Podłącz za nim node **Respond to Webhook** - ustaw Body na `JSON` i wpisz np.
   `{ "status": "ok" }`.
3. Kliknij **Listen for test event** i otwórz Test URL w przeglądarce - powinieneś zobaczyć
   swoją odpowiedź JSON.
4. Opublikuj workflow (**Publish**) i otwórz tym razem **Production URL** - efekt powinien być
   identyczny, ale bez klikania "Listen".
5. Dorzuć w ustawieniach node'a Webhook prostą **Authentication** (np. Header Auth), żeby
   nie każdy mógł wywołać Twój endpoint.

<Takeaways>
  - Node'y aplikacji działają według schematu **Resource → Operation** - opanuj go raz i obsłużysz każdy nowy node.
  - Credentials tworzysz raz i podpinasz wielokrotnie; n8n trzyma je zaszyfrowane (encryption key).
  - **API key** = szybki sekret o pełnym zakresie; **OAuth2** = ograniczona, odwoływalna zgoda przez adres callback. Publiczny HTTPS jest konieczny dla webhooków i triggerów.
  - **HTTP Request** obsłuży każde API, gdy brakuje gotowego node'a - z metodami, nagłówkami, body i autoryzacją przez credentials.
  - Webhook node odbiera zdarzenia (test vs production URL, odpowiedź przez Respond to Webhook); HTTP Request wysyła zdarzenia do cudzych webhooków.
  - Webhook od zewnętrznego dostawcy weryfikuj **podpisem HMAC**: Raw Body, node Crypto z sekretem w credentialu i porównanie przez `crypto.timingSafeEqual` z kontrolą długości; przed powtórkami chroni znacznik czasu i odsiewanie ID zdarzeń.
  - Na produkcji obsłuż **paginację**, **rate limity (429)** i błędy - łącząc Pagination, Loop Over Items, Wait oraz Retry On Fail.
  - Dane z webhooka czytasz z `$json.body`, a działający berek między dwoma workflow to najszybszy test, że Production URL, publikacja i metoda HTTP są ustawione dobrze.
</Takeaways>
