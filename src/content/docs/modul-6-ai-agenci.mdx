n8n to nie tylko "spinanie API". To także pełnoprawny orkiestrator AI: na bazie LangChain
budujesz tu asystentów, agentów decydujących o użyciu narzędzi oraz systemy RAG odpowiadające
na Twoich danych. W tym module zrozumiesz, jak te klocki działają i - co ważniejsze - kiedy
ich naprawdę potrzebujesz.

## n8n jako orkiestrator AI

Węzły AI w n8n są oparte na **LangChain** - frameworku, który dostarcza warstwę abstrakcji nad
modelami językowymi, embeddingami, bazami wektorowymi i mechanizmami pobierania danych. Dzięki
temu budujesz zaawansowane aplikacje AI bez pisania kodu integrującego - zamiast tego składasz
gotowe klocki na kanwie.

:::note[Po ludzku - LLM, prompt, token, framework]

- **LLM (model językowy)** - "mózg" AI, np. GPT od OpenAI albo Claude od Anthropic. Dostaje
  tekst i generuje odpowiedź.
- **Prompt** - polecenie lub pytanie, które wysyłasz do modelu. Im jaśniejszy prompt, tym
  lepsza odpowiedź.
- **Token** - kawałek tekstu, na jaki model dzieli słowa (z grubsza ~4 znaki). Dostawcy liczą
  koszt i limity właśnie w tokenach: dłuższy tekst = więcej tokenów = drożej.
- **Framework** - gotowy "szkielet" z zestawem narzędzi (tu: LangChain), na którym budujesz,
  zamiast pisać wszystko od zera.

:::

Kluczowe jest tu pojęcie, którego nie spotkasz w "zwykłych" node'ach: **cluster nodes**. To
grupa node'ów, które działają razem jako jeden zespół. Składają się z dwóch warstw:

### Jak to wygląda na kanwie

Root node ma na dole specjalne porty (kropki z etykietami: _Chat Model_, _Memory_, _Tool_). Do
każdego portu podpinasz odpowiedni sub-node. To inny sposób łączenia niż lewo→prawo, do którego
przywykłeś z poprzednich modułów - sub-node nie jest "kolejnym krokiem", tylko **zdolnością**,
którą wyposażasz roota.

```text
[Chat Trigger] ──► [AI Agent]  (root node, w głównym przepływie)
                       ▲ ▲ ▲
                       │ │ └── Tool        (np. Calculator, HTTP Request jako narzędzie)
                       │ └──── Memory      (np. Simple Memory / Window Buffer)
                       └────── Chat Model  (np. OpenAI / Anthropic / Ollama)
```

sub-node i działa dalej. Logika (root) jest niezależna od dostawcy (sub-node).

## AI Agent node - model, który sam decyduje

Najważniejsza różnica w całym module: **zwykłe wywołanie LLM** (Chain) wysyła prompt i odbiera
tekst - koniec. **Agent** dostaje do dyspozycji zestaw narzędzi i sam decyduje, których użyć,
w jakiej kolejności i czy w ogóle. To różnica między "odpowiedz na pytanie" a "rozwiąż problem".

### Pętla rozumowania (ReAct)

Agent nie generuje jednej odpowiedzi z marszu. Działa w cyklu **reasoning → action →
observation**, który powtarza, dopóki nie osiągnie celu:

1. **Reasoning** - analizuje żądanie i decyduje, jaki krok wykonać.
2. **Action** - wybiera narzędzie z dostępnych (np. kalkulator, HTTP Request, sub-workflow) i je wywołuje.
3. **Observation** - odbiera wynik narzędzia i ocenia, czy to wystarczy.
4. **Powtórka lub finał** - jeśli trzeba więcej danych, wraca do kroku 1; jeśli nie - formułuje finalną odpowiedź.

W praktyce: zapytaj agenta "Jaka jest dziś pogoda w Krakowie i czy brać parasol?" - sam
zdecyduje, że musi wywołać narzędzie pogodowe (action), odczyta wynik (observation), a potem na
jego podstawie napisze odpowiedź. Model bez narzędzi po prostu zmyśliłby pogodę.

### Tools Agent - domyślny typ

AI Agent node historycznie oferował kilka typów (Conversational, ReAct, OpenAI Functions, Plan
and Execute, SQL). Dziś rekomendowany i domyślny jest **Tools Agent** - korzysta z natywnego
mechanizmu "function/tool calling" nowoczesnych modeli, dzięki czemu wybór narzędzi jest
bardziej niezawodny niż w starszym podejściu ReAct opartym na parsowaniu tekstu.

<TwoCol>
  <Panel variant="neutral" title="Kiedy zwykły Chain">

    - Streszczenie tekstu, klasyfikacja, ekstrakcja danych, tłumaczenie
    - Chcesz **przewidywalności** i niższych kosztów (jedno wywołanie modelu)

  </Panel>

    - Zadanie wymaga **decyzji**: "użyć narzędzia czy nie? którego?"
    - Wieloetapowe rozumowanie, dynamiczny przepływ
    - Asystent, który może sięgnąć po dane na żywo (API, baza, wyszukiwarka)

:::caution[Agent to nie zawsze lepiej]
Agent jest droższy (kilka wywołań modelu na jedną odpowiedź) i mniej przewidywalny niż Chain.
Jeśli zadanie jest deterministyczne - streść ten tekst, sklasyfikuj to zgłoszenie - użyj Chaina.
Agent rezerwuj na sytuacje, gdzie naprawdę potrzeba _decyzji_, a nie pojedynczego przekształcenia.
:::

## Modele: OpenAI, Anthropic i lokalne (Ollama)

Model językowy podpinasz jako sub-node typu **Chat Model** do portu _Chat Model_ roota. n8n
wspiera wielu dostawców - każdy z nich to osobny sub-node, który potrzebuje własnych
**credentials** (klucz API lub adres lokalnego serwera).

### Jak podpiąć dostawcę modelu

1. Dodaj root node (np. `AI Agent` lub `Basic LLM Chain`).
2. Kliknij port _Chat Model_ i wybierz sub-node dostawcy, np. **OpenAI Chat Model**, **Anthropic Chat Model** lub **Ollama Chat Model**.
3. Skonfiguruj credentials: dla chmury klucz API, dla Ollamy adres lokalnego serwera (np. `http://localhost:11434`).
4. Wybierz konkretny model (np. `gpt-4o-mini`, `claude-...`, `llama3`) i parametry (temperatura itp.).

| Wymiar | OpenAI (chmura) | Anthropic (chmura) | Ollama (lokalnie) |
| --- | --- | --- | --- |
| Sub-node | OpenAI Chat Model | Anthropic Chat Model | Ollama Chat Model |
| Credentials | Klucz API | Klucz API | Adres serwera (URL) |
| Gdzie trafiają dane | Na serwery dostawcy | Na serwery dostawcy | Zostają u Ciebie |
| Koszt | Per token (zmienny) | Per token (zmienny) | Tylko sprzęt/prąd |
| Prywatność | Zależna od polityki dostawcy | Zależna od polityki dostawcy | Pełna - dane nie wychodzą |
| Jakość / moc | Bardzo wysoka | Bardzo wysoka | Zależna od modelu i sprzętu |
| Wymagania | Tylko klucz | Tylko klucz | Mocny serwer/GPU |
| Najlepsze gdy… | Maksymalna jakość, szybki start | Długi kontekst, ostrożne odpowiedzi | RODO, dane wrażliwe, kontrola kosztów |

:::tip[Dlaczego lokalne modele (Ollama)]
Gdy przetwarzasz dane wrażliwe (medyczne, prawne, wewnętrzne dokumenty firmy), wysyłanie ich do
chmury bywa problemem - RODO, tajemnica handlowa, polityka klienta. Ollama uruchamia model **na
Twoim serwerze**: dane nie opuszczają infrastruktury, a koszt jest stały (sprzęt) zamiast rosnąć
z każdym tokenem. Cena: potrzebujesz mocnego sprzętu, a jakość lokalnych modeli zwykle ustępuje
topowym modelom chmurowym. To klasyczny kompromis prywatność/koszt vs jakość/wygoda.
:::

## Pamięć i narzędzia (memory & tools)

Sam model nie pamięta poprzednich wiadomości - każde wywołanie jest "bez historii". Aby
asystent prowadził rozmowę, podpinasz sub-node **Memory**. Aby mógł coś _zrobić_ (a nie tylko
gadać), podpinasz **Tools**.

### Pamięć (memory)

Pamięć przechowuje historię konwersacji i dokleja ją do kolejnych zapytań, żeby agent
"pamiętał kontekst". Typy w n8n:

- **Simple Memory (Window Buffer)** - trzyma ostatnie N wiadomości w pamięci instancji.
  Najprostsze, świetne na start; znika po restarcie.
- **Postgres / Redis / MongoDB Chat Memory** - historia trwała w bazie. Potrzebna, gdy rozmowa
  ma przetrwać restart i działać przy wielu użytkownikach (klucz sesji).

"Window buffer" oznacza, że pamiętane jest **okno** ostatnich wiadomości - nie cała historia.
To celowe: kontekst modelu jest ograniczony, a każdy doklejony token kosztuje. Im większe okno,
tym więcej kontekstu, ale i wyższy koszt.

### Narzędzia (tools)

Narzędzia to zdolności, które agent może wywołać samodzielnie. Przykłady: `Calculator`, `HTTP
Request Tool`, `Wikipedia`, `Vector Store QA Tool`, `Code Tool`, a także **inny workflow jako
narzędzie** (Call n8n Workflow Tool).

:::tip[Workflow jako tool - najmocniejszy wzorzec]
To spina ten moduł z [Modułem 5](/modul-5-kod-sub-workflow): dowolny Twój sub-workflow (np.
"dodaj klienta do CRM", "wystaw fakturę") możesz wystawić agentowi jako narzędzie. Agent sam
zdecyduje, kiedy je wywołać i z jakimi parametrami. Cała moc n8n - setki integracji - staje się
wtedy "rękami" agenta.
:::

## MCP - n8n jako klient i jako serwer

**MCP (Model Context Protocol)** to otwarty standard łączenia aplikacji AI z zewnętrznymi
narzędziami i danymi. Twórcy porównują go do portu USB-C: jeden wspólny "wtyk" zamiast osobnej
integracji dla każdej pary aplikacja-narzędzie
([modelcontextprotocol.io](https://modelcontextprotocol.io/docs/getting-started/intro)).
Protokół opublikowało Anthropic w listopadzie 2024
([Wikipedia](https://en.wikipedia.org/wiki/Model_Context_Protocol)), dziś obsługują go m.in. Claude, ChatGPT,
Cursor i VS Code.

:::note[Po ludzku - serwer i klient MCP]

- **Serwer MCP** - coś, co wystawia narzędzia: "oto lista rzeczy, które umiem zrobić, i jakie
  parametry przyjmują".
- **Klient MCP** - aplikacja AI, która tę listę pobiera i pozwala modelowi wywoływać narzędzia.

Dla agenta różnica między "narzędzie podpięte w n8n" a "narzędzie z serwera MCP" jest żadna -
w obu przypadkach widzi nazwę, opis i parametry. Zmienia się tylko to, gdzie narzędzie mieszka.

:::

W n8n MCP pojawia się w trzech miejscach, które łatwo pomylić. Każde działa w innym kierunku:

| | MCP Client Tool | MCP Server Trigger | Serwer MCP instancji |
| --- | --- | --- | --- |
| Kierunek | n8n korzysta z cudzego serwera | n8n wystawia **jeden workflow** jako serwer | n8n wystawia **całą instancję** |
| Kto jest klientem | Twój AI Agent w n8n | Claude, Cursor, inny agent | Claude, Lovable, inny klient AI |
| Co widzi klient | narzędzia obcego serwera | narzędzia podpięte pod trigger | workflow z włączonym dostępem MCP |
| Gdzie to włączasz | sub-node przy AI Agencie | trigger na kanwie | Settings → Instance-level MCP |

### MCP Client Tool - cudzy serwer jako narzędzie agenta

**Kiedy:** usługa, z której chcesz korzystać, ma już serwer MCP (dokumentacja, CRM, wyszukiwarka,
narzędzia deweloperskie). Zamiast budować dziesięć narzędzi HTTP Request, podpinasz jeden
sub-node i agent dostaje cały zestaw.

1. Do portu _Tool_ węzła **AI Agent** podepnij sub-node **MCP Client Tool**.
2. W polu **Endpoint** wklej adres serwera MCP.
3. **Server Transport** zostaw na **HTTP Streamable** - to domyślny transport w aktualnej wersji
   node'a. Starszy SSE wybierasz tylko wtedy, gdy serwer nie obsługuje nowszego.
4. **Authentication:** `None`, `Bearer Auth`, `Header Auth`, `Multiple Headers Auth` (kilka
   nagłówków naraz, np. klucz API i nazwa użytkownika) albo `MCP OAuth2`.
5. **Tools to Include:** `All`, `Selected` albo `All Except`. Wybieraj `Selected` - agent
   dostaje wtedy tylko te narzędzia, których naprawdę potrzebuje.

Usługi z rejestru serwerów MCP n8n podłączysz prościej, prosto z panelu node'ów, bez ręcznego
zakładania credentials
([docs: MCP Client Tool](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolmcp)).

:::note[Dokumentacja a node w edytorze]
Stan na listopad 2026 strona dokumentacji opisuje jeszcze pierwszą wersję node'a z polem
**SSE Endpoint**. W edytorze n8n 2.x zobaczysz nowszą wersję: pole **Endpoint**, wybór
**Server Transport** i opcję **Timeout** (domyślnie 60 sekund). Nazwy pól w tej sekcji podaję
według edytora
([kod node'a](https://github.com/n8n-io/n8n/blob/master/packages/@n8n/nodes-langchain/nodes/mcp/McpClientTool/McpClientTool.node.ts)).
:::

### Mini-przykład: agent pytający o dokumentację repozytorium

Weźmy serwer, który nie wymaga konta ani klucza: **DeepWiki MCP** od Cognition. Odpowiada na
pytania o publiczne repozytoria GitHuba, jest darmowy i działa bez uwierzytelniania
([docs DeepWiki MCP](https://docs.devin.ai/work-with-devin/deepwiki-mcp)).

1. Zbuduj **Chat Trigger** → **AI Agent** z dowolnym Chat Modelem (lokalna Ollama też wystarczy)
   i **Simple Memory**.
2. Do portu _Tool_ podepnij **MCP Client Tool**: Endpoint `https://mcp.deepwiki.com/mcp`,
   Server Transport **HTTP Streamable**, Authentication **None**.
3. W **Tools to Include** wybierz `Selected` i zaznacz `ask_question`.
4. W oknie czatu zapytaj: "Korzystając z narzędzia, sprawdź w repozytorium n8n-io/n8n, jak
   działa MCP Server Trigger."
5. W logach wykonania zobaczysz wywołanie `ask_question` i odpowiedź serwera, na której agent
   zbudował swoją.

Jedyny koszt to tokeny modelu - a przy Ollamie nawet tego nie ma.

### MCP Server Trigger - Twój workflow jako serwer MCP

**Kiedy:** chcesz, żeby Claude, Cursor albo agent w innej aplikacji korzystał z Twoich
automatyzacji. Przykład: zespół pracuje w Claude, a Ty dajesz mu narzędzia "sprawdź status
zamówienia" i "dodaj zadanie do CRM", zbudowane w n8n.

Ten trigger działa inaczej niż wszystkie poznane do tej pory. Nie przekazuje danych do
następnego node'a - podpinasz do niego **wyłącznie narzędzia**, a klient MCP pobiera ich listę
i wywołuje je, kiedy uzna za stosowne. Własny workflow wystawisz jako narzędzie przez
**Custom n8n Workflow Tool** (ten sam wzorzec "workflow jako tool" co wyżej).

  caption="MCP Server Trigger nie ma następnego kroku. Klient AI pobiera listę podpiętych narzędzi i sam decyduje, które wywołać."

    Klient AI (Claude, Cursor):robot @violet -Bearer-> MCP Server Trigger (Twój workflow):server @pink
    Workflow Tool (dodaj zadanie do CRM):sitemap @amber
    HTTP Request (jako narzędzie):globe @blue
    Calculator:calculator @slate
    MCP Server Trigger <- Workflow Tool, HTTP Request, Calculator
  `}
/>

1. Utwórz nowy workflow i dodaj **MCP Server Trigger**.
2. Podepnij narzędzia: **Custom n8n Workflow Tool** wskazujący Twój sub-workflow, HTTP Request,
   Calculator - cokolwiek ma być dostępne dla klienta. Każdemu narzędziu daj jasny opis, bo to
   on decyduje, czy model go użyje.
3. **Authentication:** `Bearer Auth` albo `Header Auth`; od wersji 2 node'a także
   `n8n User Auth (OAuth2)`, czyli logowanie kontem n8n. `None` zostaw wyłącznie na testy
   lokalne.
4. **Path** jest domyślnie losowy - nie zmieniaj go na coś łatwego do zgadnięcia.
5. Opcjonalne **Instructions** trafiają do klienta przy połączeniu - opisz w nich, do czego
   służą narzędzia i w jakiej kolejności ich używać.
6. Testuj na **Test URL**, a gdy działa, opublikuj workflow - dopiero wtedy działa
   **Production URL**. Wykonania produkcyjne nie pojawiają się w edytorze, tylko w zakładce
   _Executions_ workflow.

Trigger obsługuje transporty SSE i streamable HTTP, ale nie stdio. Klient, który zna tylko
stdio (np. Claude Desktop), łączy się przez pośrednika `mcp-remote` uruchamianego `npx` -
dokumentacja podaje gotowy wpis do konfiguracji z nagłówkiem `Authorization: Bearer …`
([docs: MCP Server Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger)).

:::caution[Dwie pułapki produkcyjne]

- **Reverse proxy** (nginx, Traefik) musi mieć wyłączone buforowanie dla ścieżki MCP, inaczej
  połączenia SSE i streamable HTTP zrywają się albo gubią odpowiedzi.
- **Queue mode z kilkoma replikami webhooków** - wszystkie żądania `/mcp*` kieruj do jednej,
  dedykowanej repliki. Konfigurację skalowania omawiam w [Module 7](/modul-7-produkcja).

:::

### Serwer MCP instancji - cała instancja dla klienta AI

Trzecia funkcja to nie node, tylko ustawienie instancji. Klient AI (Claude Desktop, Lovable
i inne) łączy się z **całym n8n** jednym połączeniem i dostaje gotowy zestaw narzędzi:
wyszukiwanie workflow, uruchamianie tych, które mu udostępnisz, a od n8n 2.13 także tworzenie
i edycję workflow oraz tabel danych
([docs: n8n MCP server](https://docs.n8n.io/connect/connect-to-n8n-mcp-server)).

1. Owner lub admin włącza go w **Settings → Instance-level MCP → Enable MCP access**.
2. Dostęp jest **opt-in per workflow**: przełącznik **Available in MCP** w ustawieniach workflow
   albo hurtowo dla projektu lub folderu przez **Manage MCP access**. Opcja **Auto-expose new
   workflows** jest domyślnie wyłączona - i niech tak zostanie.
3. Klienta łączysz przez **OAuth** (zalecane) albo osobisty token z zakładki **API key**.
   Wygenerowanie nowego tokenu unieważnia poprzedni.
4. W self-hostingu wyłączysz całą funkcję zmienną `N8N_DISABLED_MODULES=mcp`.

**Kiedy który?** MCP Server Trigger, gdy chcesz wystawić **wąski, zaprojektowany przez siebie**
zestaw narzędzi, z osobnym tokenem. Serwer instancji, gdy sam pracujesz w Claude czy Cursorze
i chcesz, żeby model uruchamiał albo budował Twoje workflow - to bliższe temu, co robi
[n8n Assistant z Modułu 9](/modul-9-n8n-assistant), tylko z zewnętrznego klienta.

:::danger[Wystawiasz akcje, nie tylko dane]
Każde narzędzie wystawione przez MCP to akcja, którą obcy model wykona **Twoimi
uprawnieniami** - z credentials zapisanymi w n8n. Trzy zasady:

- Wystawiaj najmniejszy potrzebny zestaw narzędzi. Akcje nieodwracalne (usuwanie, płatności,
  wysyłka do klientów) chowaj za potwierdzeniem człowieka.
- Zawsze uwierzytelnianie. Adres MCP Server Triggera bez tokenu to publiczny endpoint, który
  każdy może odpytać i wywołać.
- Na serwerze instancji pamiętaj, że dostęp nie jest dzielony per klient: każdy podłączony
  klient widzi wszystkie workflow z włączonym MCP, do których masz dostęp. Narzędzia z obcych
  serwerów (MCP Client Tool) traktuj jak obcy kod: to serwer decyduje, jakie opisy narzędzi
  i jakie odpowiedzi trafią do Twojego agenta, więc podłączaj tylko te, którym ufasz.
  Zagrożenia po stronie samego protokołu opisuje
  [MCP: Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices).

:::

## RAG: bazy wektorowe i embeddingi

Model zna tylko to, na czym był trenowany - nie zna Twoich dokumentów, regulaminów ani bazy
wiedzy. **RAG** (Retrieval-Augmented Generation) rozwiązuje to: zanim model odpowie, najpierw
_wyszukuje_ pasujące fragmenty Twoich danych i dokłada je do promptu. Efekt: odpowiedzi oparte
na Twoich danych, z mniejszą skłonnością do zmyślania.

### Trzy pojęcia, które musisz znać

<CardGrid>
  <ConceptCard icon="fa-vector-square" title="Embeddings">
    Zamiana tekstu na wektor liczb oddający jego _znaczenie_. Podobne treści mają podobne
    wektory - to pozwala wyszukiwać "po sensie", nie po słowach kluczowych.
  </ConceptCard>
  <ConceptCard icon="fa-database" title="Vector store">
    Baza wektorowa (np. Pinecone, Qdrant, PGVector, Supabase, Chroma) przechowująca embeddingi
    fragmentów i umożliwiająca szybkie wyszukiwanie najbliższych.
  </ConceptCard>
  <ConceptCard icon="fa-magnifying-glass" title="Retrieval">
    Pobranie z bazy fragmentów najbardziej zbliżonych znaczeniowo do pytania. To one trafiają do
    promptu jako kontekst dla modelu.
  </ConceptCard>
</CardGrid>

### Przepływ RAG - od dokumentu do odpowiedzi

RAG dzieli się na dwie fazy. Najpierw **jednorazowo (lub cyklicznie) wczytujesz dane** do bazy
(ingest), a potem **przy każdym pytaniu** z niej korzystasz.

1. **Ingest - wczytaj dokumenty**

   Pobierz źródła (pliki, strony, baza, Google Drive) i podziel je na fragmenty (text splitter),
   bo całych dokumentów się nie wektoryzuje.

2. **Embed - zamień na wektory**

   Każdy fragment przepuść przez sub-node Embeddings (np. OpenAI / Ollama), żeby otrzymać
   wektor znaczenia.

3. **Store - zapisz w bazie wektorowej**

   Wektory wraz z tekstem trafiają do vector store. Tę fazę robisz raz przy starcie i powtarzasz,
   gdy dochodzą nowe dane.

4. **Retrieve - wyszukaj przy pytaniu**

   Pytanie użytkownika też zamieniasz na wektor i pobierasz z bazy najbliższe fragmenty
   (retriever / Vector Store QA Tool).

5. **Answer - odpowiedz na kontekście**

   Pobrane fragmenty + pytanie trafiają do modelu (Question and Answer Chain lub agent z
   narzędziem QA), który formułuje odpowiedź opartą na Twoich danych.

:::note[RAG kontra dotrenowanie modelu]
Często słyszysz "wytrenuj model na naszych danych". W większości przypadków RAG jest tańszy,
szybszy i łatwiejszy do aktualizacji - dorzucasz nowy dokument do bazy i gotowe, bez kosztownego
treningu. RAG nie zmienia modelu; podaje mu właściwy kontekst we właściwym momencie.
:::

## Budowa chatbota / asystenta

Mając już klocki (root, model, pamięć, narzędzia, RAG), zbudowanie asystenta to kwestia ich
poskładania. Wejściem rozmowy jest **Chat Trigger** - node, który uruchamia workflow z okna
czatu i przekazuje wiadomość użytkownika dalej.

### Prosty asystent - minimalny zestaw

1. **Chat Trigger**

   Dodaj `Chat Trigger` jako wyzwalacz. Daje wbudowane okno czatu do testów i przyjmuje kolejne
   wiadomości.

2. **AI Agent (root)**

   Podłącz `AI Agent` do triggera. To on poprowadzi rozmowę i zdecyduje o użyciu narzędzi.

3. **Chat Model + Memory**

   Do agenta podepnij sub-node modelu (np. OpenAI/Anthropic/Ollama) i pamięć (Simple Memory), by
   rozmowa miała kontekst.

4. **Narzędzia**

   Dokumentacja AI Agenta wymaga podpięcia co najmniej jednego narzędzia - na start wystarczy
   Calculator. Potem dodaj kolejne, np. **Vector Store QA Tool** wskazujący na bazę z Twoimi dokumentami, by
   asystent odpowiadał na własnej wiedzy (RAG).

:::tip[Co dalej]
Działający w oknie czatu asystent to dopiero prototyp. Dalej: podmień Chat Trigger na
**Webhook** i podłącz front (strona, Slack, Telegram, WhatsApp), dodaj trwałą pamięć
(Postgres/Redis) z kluczem sesji per użytkownik, oraz **system prompt** definiujący rolę i
granice asystenta. Wdrożenie produkcyjne omawiam w [Module 7](/modul-7-produkcja).
:::

## Agenci 24/7 - wzorce i pułapki

Asystent w czacie reaguje na człowieka. Agent 24/7 działa **sam**: wyzwalany zdarzeniem lub
harmonogramem, podejmuje decyzje i wykonuje akcje bez nadzoru. To potężne - i właśnie dlatego
wymaga ostrożności.

### Typowy wzorzec

```text
[Trigger]  ──►  [AI Agent]  ──►  [akcja / zapis wyniku]
 webhook,         ▲ ▲ ▲
 schedule,        │ │ └── Tools  (HTTP, sub-workflow, baza, QA na dokumentach)
 nowy mail        │ └──── Memory (kontekst sesji, jeśli potrzebny)
                  └────── Chat Model
```

Przykłady: agent klasyfikujący i wstępnie odpowiadający na maile wsparcia, agent monitorujący
zgłoszenia i eskalujący pilne, agent zbierający dane i tworzący codzienny raport. Wzorzec ten
sam: _trigger → agent → narzędzia → akcja_.

:::caution[Świadomie, nie ślepo - pułapki agentów bez nadzoru]

- **Koszty tokenów** - agent robi kilka wywołań modelu na jedno zadanie, a działa 24/7. Bez
  limitów rachunek potrafi eksplodować. Ustaw limity, monitoruj zużycie, taniej model do
  prostych kroków.
- **Pętle** - agent może wpaść w cykl "myśl → działaj → myśl..." bez końca. Ustaw **max
  iterations** i timeouty.
- **Halucynacje** - model potrafi pewnie zmyślać. Przy realnych akcjach (wysłanie maila, zmiana
  danych) to ryzykowne. Ratunkiem jest RAG, walidacja i ograniczone narzędzia.
- **Brak kontroli nad akcjami** - agent z narzędziem "usuń rekord" może go użyć błędnie. Dawaj
  **najmniejszy potrzebny zestaw narzędzi**, a akcje nieodwracalne chowaj za potwierdzeniem
  człowieka (human-in-the-loop).

:::

:::note[Zasada wdrożenia]
Zacznij od agenta, który **proponuje**, a nie **wykonuje**: niech generuje szkic odpowiedzi czy
listę akcji do akceptacji. Gdy zaufasz jego decyzjom na danych produkcyjnych, stopniowo zdejmuj
ręczne potwierdzenia. Autonomię nadawaj _etapami_, nie od razu.
:::

:::note[A co z n8n Assistant?]
n8n ma też własnego asystenta, który buduje workflow **za Ciebie** - i to coś zupełnie
innego niż AI Agent z tego modułu. Agent jest węzłem w Twoim workflow i pracuje dla Twoich
użytkowników; Assistant siedzi w edytorze i pracuje dla Ciebie, w czasie gdy budujesz.
Ma własny moduł, bo ma własny warunek wstępny i własne pułapki:
[Moduł 9: n8n Assistant](/modul-9-n8n-assistant).
:::

## Ćwiczenie: lokalny chatbot z Ollamą

Pora poskładać klocki z tego modułu w działającą całość. Zbudujesz chatbota z charakterem,
który działa na modelu uruchomionym na Twoim komputerze: Chat Trigger, AI Agent, model z
Ollamy, pamięć i jedno narzędzie. Bez klucza API i bez płacenia za tokeny.

- **Cel:** chatbot, który odpowiada w nadanej mu roli, pamięta, co mu powiedziałeś, i sam
  sięga po narzędzie Calculator, gdy dostaje działanie do policzenia.
- **Czas:** 30-45 minut, plus czas pobierania modelu (kilka GB).
- **Potrzebujesz:** self-hosted n8n oraz [Ollamy](https://ollama.com/download) na tym samym
  komputerze albo w tej samej sieci. Na n8n Cloud lokalnej Ollamy nie podepniesz - wybierz
  wariant z modelem w chmurze poniżej.

<Flow
  title="cwiczenie-chatbot-ollama"
  alt="Schemat ćwiczenia: Chat Trigger przekazuje wiadomość do AI Agenta, pod którego od spodu podpięte są Ollama Chat Model, Simple Memory i narzędzie Calculator"
  caption="Jeden krok w głównym przepływie i trzy zdolności podpięte od spodu: model, pamięć i narzędzie."
  spec={`
    Ollama Chat Model (lokalny model):microchip @blue
    Simple Memory (okno rozmowy):database @green
    Calculator (narzędzie):calculator @amber
    Chat Trigger (okno czatu):comments @sky -> AI Agent (root node):robot @pink
    AI Agent <- Ollama Chat Model, Simple Memory, Calculator
  `}
/>

### Kroki

1. **Pobierz model.** W terminalu uruchom `ollama pull llama3.2:3b` (alternatywnie
   `qwen2.5:3b`). Oba modele mają w bibliotece Ollamy oznaczenie _tools_, czyli obsługują
   wywoływanie narzędzi - bez tego agent nie użyje Calculatora. Sprawdź listę poleceniem
   `ollama list`.
2. **Chat Trigger.** W nowym workflow dodaj trigger _On chat message_ (node **Chat Trigger**).
   Opcję _Make Chat Publicly Available_ zostaw wyłączoną - na razie rozmawiasz z botem tylko
   z edytora.
3. **AI Agent.** Podłącz za triggerem **AI Agent**. W _Options_ → _Add Option_ wybierz
   **System Message** i nadaj botowi rolę, np. "Jesteś zrzędliwym, ale pomocnym bibliotekarzem.
   Odpowiadasz po polsku, maksymalnie w trzech zdaniach. Działania matematyczne zawsze liczysz
   narzędziem Calculator".
4. **Model.** Do portu _Chat Model_ podepnij **Ollama Chat Model**. Utwórz credential Ollama
   z _Base URL_ dopasowanym do Twojej instalacji:
   - n8n i Ollama na tym samym komputerze, bez Dockera: `http://127.0.0.1:11434`,
   - n8n w Dockerze, Ollama na komputerze-gospodarzu: `http://host.docker.internal:11434`
     (na Linuksie kontener startujesz z `--add-host=host.docker.internal:host-gateway`, a Ollama
     musi nasłuchiwać na `0.0.0.0`, nie tylko na `127.0.0.1`),
   - oba w Dockerze, we wspólnej sieci: `http://ollama:11434` (nazwa kontenera Ollamy).

   Wybierz z listy pobrany model.
5. **Pamięć i narzędzie.** Do portu _Memory_ podepnij **Simple Memory**, a do portu _Tool_ -
   **Calculator**. Dokumentacja AI Agenta wymaga co najmniej jednego narzędzia, a Calculator
   nie potrzebuje żadnych credentials.
6. **Rozmawiaj.** Kliknij **Open chat** u dołu kanwy i przeprowadź krótką rozmowę: przedstaw się,
   zadaj pytanie, a potem poproś o działanie, np. "Ile to 1234 razy 5678?".

<details>
<summary>Sprawdź, czy działa</summary>

- Bot odpowiada w nadanej roli i po polsku, a nie jak domyślny "pomocny asystent".
- Po dwóch-trzech wiadomościach zapytaj "Jak mam na imię?" - bot pamięta, bo Simple Memory
  dokleja historię rozmowy do kolejnych zapytań.
- Na pytanie o 1234 × 5678 pada wynik **7 006 652**, a w logach wykonania pod oknem czatu
  widać wywołanie Calculatora. Jeśli wynik jest inny i Calculatora w logach nie ma, model
  "policzył" z pamięci - czyli zgadywał.
- W zakładce Executions każda Twoja wiadomość to osobne wykonanie workflow.

</details>

### Wariant z modelem w chmurze

Bez karty graficznej model 3B na samym procesorze odpowiada wolno, a na n8n Cloud lokalnej
Ollamy nie użyjesz wcale. Wtedy zamiast **Ollama Chat Model** podepnij **OpenAI Chat Model**
albo **Anthropic Chat Model** z kluczem API i wybierz najtańszy model z listy - do tego
ćwiczenia w zupełności wystarczy. Resztę workflow zostawiasz bez zmian, to właśnie zaleta
sub-node'ów. Pamiętaj tylko, że tu płacisz za każdy token: zanim zostawisz takiego bota
włączonego, przeczytaj [ostrzeżenie o kosztach agentów](#agenci-247---wzorce-i-pułapki),
policz koszt według [wyliczeń tokenów AI](/ile-kosztuje-n8n#ile-kosztują-tokeny-ai-w-workflow)
i ustaw limit wydatków w panelu dostawcy.

### Wariant dla zaawansowanych

- **Narzędzie z prawdziwymi danymi.** Dodaj drugie narzędzie, **HTTP Request Tool**, z URL-em
  `https://wttr.in/Warszawa?format=j1` i opisem "Pobiera aktualną pogodę dla Warszawy". Zapytaj
  bota, czy wziąć parasol. To ten sam serwis co w
  [ćwiczeniu z Modułu 2](/modul-2-interfejs-pierwszy-workflow#ćwiczenie-pogoda-z-wttrin), tyle że
  teraz o zapytaniu decyduje model.
- **Czat dla innych.** Włącz w Chat Triggerze _Make Chat Publicly Available_, ustaw
  _Authentication_ na **Basic Auth** i opublikuj workflow (**Publish**). Dostaniesz adres
  czatu, który możesz dać znajomemu. Przy _Authentication_ ustawionym na _None_ z czatu może
  korzystać każdy, kto zna adres - a każda wiadomość obciąża Twój sprzęt albo Twój budżet
  na tokeny.

### Typowe pułapki

| Objaw | Przyczyna |
| --- | --- |
| `ECONNREFUSED ::1:11434` przy teście credentiala | `localhost` rozwiązał się do IPv6, a Ollama słucha na IPv4 - wpisz `http://127.0.0.1:11434` |
| `ECONNREFUSED` z n8n w Dockerze | `localhost` w kontenerze to sam kontener, nie Twój komputer - użyj `host.docker.internal` albo nazwy kontenera Ollamy |
| Pusta lista modeli w Ollama Chat Model | Model nie został pobrany - `ollama pull` i odśwież listę |
| Agent nie startuje i domaga się narzędzia | Do portu _Tool_ nic nie jest podpięte - dodaj choćby Calculator |
| Błąd _No prompt specified_ | _Prompt_ w AI Agencie ustawiony na _Connected Chat Trigger Node_, a wiadomość nie przychodzi z Chat Triggera - podłącz trigger albo przestaw na _Define below_ |
| Bot zapomina, co mówiłeś przed chwilą | Simple Memory niepodpięta albo podpięta do złego portu |
| Wynik działania jest zły, a Calculatora nie ma w logach | Model nie obsługuje wywoływania narzędzi albo jest za mały - wybierz model z oznaczeniem _tools_ |
| Odpowiedź przychodzi po minucie | Model za duży na Twój sprzęt - zejdź do mniejszego wariantu albo przejdź na model w chmurze |

Źródła do kroków i pułapek (stan na listopad 2026):
[Chat Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.chattrigger/),
[AI Agent](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent/),
[Ollama credentials](https://docs.n8n.io/integrations/builtin/credentials/ollama/),
[typowe problemy Ollama Chat Model](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.lmchatollama/common-issues/)

w dokumentacji n8n.

:::caution[Simple Memory a tryb kolejki]
Simple Memory trzyma historię w pamięci procesu. Jeśli Twoja instancja działa w trybie kolejki
(queue mode, kilka workerów), dokumentacja n8n odradza ten node w opublikowanym workflow -
kolejne wiadomości mogą trafić do różnych workerów. Do ćwiczenia w edytorze to bez znaczenia,
na produkcję wybierz pamięć w bazie (Postgres, Redis).
:::

## Sprawdź się

Zanim ruszysz dalej, odpowiedz sobie na te pytania - na głos albo w dwóch zdaniach na kartce.
Jeśli przy którymś się zawahasz, wróć do podlinkowanej sekcji.

1. Czym różni się root node od sub-node'a w cluster node - i dlaczego sub-node sam nie uruchamia
   workflow? Jeśli nie masz pewności - [Jak to wygląda na kanwie](#jak-to-wygląda-na-kanwie).
2. Umiesz opisać własnymi słowami cykl **reasoning → action → observation**, w którym działa
   agent, zanim sformułuje finalną odpowiedź? Jeśli nie masz pewności - [Pętla rozumowania
   (ReAct)](#pętla-rozumowania-react).
3. Dlaczego "okno" pamięci (window buffer) nie przechowuje całej historii rozmowy - i co się
   dzieje z kosztem zapytań, gdy zbyt mocno je rozszerzysz? Jeśli nie masz pewności - [Pamięć
   (memory)](#pamięć-memory).
4. Które kroki przepływu RAG wykonujesz tylko raz (albo cyklicznie), a które przy każdym pytaniu
   użytkownika? Jeśli nie masz pewności - [Przepływ RAG - od dokumentu do

<Takeaways>
  - Węzły AI w n8n bazują na LangChain i działają jako cluster nodes: root node + sub-node'y (model, memory, tools).
  - Sub-node to "zdolność" podpinana do roota od spodu - wymieniasz dostawcę modelu bez przebudowy workflow.
  - Chain = jednokrokowe, przewidywalne, tańsze. Agent = sam decyduje o użyciu narzędzi, wieloetapowy, droższy.
  - Tools Agent to dziś domyślny, najbardziej niezawodny typ agenta.
  - Modele podpinasz jako Chat Model + credentials; Ollama (lokalnie) = prywatność i stały koszt vs jakość chmury.
  - MCP w n8n w trzech kierunkach: MCP Client Tool (agent korzysta z cudzego serwera), MCP Server Trigger (Twój workflow jako serwer), serwer instancji (klient AI widzi wybrane workflow) - zawsze z uwierzytelnianiem i najmniejszym zestawem narzędzi.
  - RAG = embeddings + vector store + retrieval; przepływ: ingest → embed → store → retrieve → answer.
  - Chatbota startujesz od Chat Trigger + AI Agent + model + pamięć + co najmniej jedno narzędzie; kolejne narzędzia i RAG dokładasz wedle potrzeb.
  - Lokalny chatbot na Ollamie nic nie kosztuje za tokeny, ale wymaga modelu z obsługą narzędzi i poprawnego _Base URL_ (`127.0.0.1`, `host.docker.internal` albo nazwa kontenera).
  - Agenci 24/7: pilnuj kosztów, pętli (max iterations), halucynacji i kontroli nad akcjami - autonomię nadawaj etapami.
  - Assistant z [Modułu 9](/modul-9-n8n-assistant) to co innego niż agent: on buduje workflow, agent w nim pracuje.
</Takeaways>
